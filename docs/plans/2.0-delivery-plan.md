# djust 2.0: delivery plan

Status: draft, 2026-10-19. This document turns the direction recorded in [the 2.0 plan](2.0.0-plan.md#direction-settled-2026-10-19) into scoped PRs, an acceptance matrix and a list of what is still open. It makes no code changes and approves no API, wire format or date.

Baseline: `origin/2.0` at `508043e9` (#3551). Line references are to that tree and move as PRs land. Related plans: [2.0-exposure-flip.md](2.0-exposure-flip.md) (exposure PRs 0–11) and [2.0-transport-core.md](2.0-transport-core.md) (TC1–TC11).

## 1. PR and dependency sequence

The phases run in this order: inventory → 1.4 bridge → core contracts → real-app migration → 2.0 flips and removals → transport convergence → retained-feature ports → release gates. Phases overlap where the dependencies allow it; the **Depends on** column is the rule, not the phase order. "1.4" PRs target `main`; "2.0" PRs target `2.0`.

## 3. Still open — not decided

The 2026-10-19 direction does not decide any of these. Each needs its own design review and owner decision.

- The exact strict-mode API: setting name, scope, precedence against per-handler and per-view overrides and reserved fields. It must not silently grant exposure or fall back to legacy semantics.
- The wire format: the common render, error and poll frames, protocol or version negotiation, and the single-frame proposal (transport-core TC9, §6 Q1).
- The client decisions D1–D5 and D7. D6 (the SSE `layout` drop) is settled: fixed on main in #3527 and backported to 1.2 in #3556.
- The storage and executor APIs, and which adapters are selected (Celery is a candidate only).
- Retention, retries, leases and fencing, and cancellation.
- Production diagnostics policy (exposure-flip §6 Q3) and public-page and service-worker caching (§6 Q5).
- Release dates.
- Also carried forward from plan §8 and the sub-plans: the capability API, SSE subscriptions, API dispatchers as `Call` turns, cursor and effect ordering, retained-history expiry, snapshot resync, the component-system benchmark, deploy-CLI move, `@client_state` / `@optimistic` / `@cache`, the Rust component crate, test strategy and per-event cost.

## 5. Proposal outline: new ADR on shared state, operations and durable jobs

No ADR number is assigned. This is an outline for the C0 PR, not a decision.

**Context.** Logical view state lives on the Python view object and its connection. The background runner is process-local and view-local (`mixins/async_work.py:61` `run_async_callback`: coroutine functions run on the event loop, sync callables on a thread). The HTTP fallback drops queued background work and logs once per view class (#3544, `mixins/request.py:58`). SSE sessions (`sse.py:76`) and admin progress jobs (`admin_ext/progress.py:67`) are process-local. Celery appears in the docs only as an external caller of `push_to_view` (`docs/website/advanced/server-push.md:57`).

**Decision direction** (from the owner's 2026-10-19 direction):

- A pluggable shared-state and results backend, with Redis, database and other implementations, behind a capability contract.
- A separate, pluggable executor. Shared storage alone does not run jobs, and pub/sub alone is neither retained state nor a durable result store.
- Durable named jobs with serializable inputs, explicit ownership and retained status, progress and results, served by any authorized node over push or polling.
- Local bound callbacks remain, with a documented, weaker connection- or process-scoped lifetime.
- Operation keys for deduplication and outcome reconciliation. An error after commit never authorizes a blind replay. No exactly-once guarantee for external effects; applications keep their own idempotency and transaction handling.
- Notifications speed delivery; the persisted outcome is the source of truth.
- Core stays one distribution; adapters are optional extras. Celery is a candidate adapter only.

**Design still required:** backend atomicity, versioning (compare-and-set) and capability negotiation; tenant ownership and permissions; job registration and serialization; transaction-to-enqueue consistency (for example an outbox); retries and backoff; leases and fencing; cancellation and completion races; retention and expiry; downgrade behaviour when a durability capability is missing; adapter conformance tests; worker topology and failure recovery; migrations of stored records.

**Alternatives to record:** state on the connection with sticky routing (rejected by direction); pub/sub only (not durable); one required executor such as Celery (rejected: not mandatory); inline execution on HTTP (rejected as a substitute for durable work).

**Acceptance:** the "Uncertain POST", "Updates", "Durable jobs" and "Shared backends" rows of §2.
