# djust 2.0.0 plan

Status: **draft, opened 2026-10-16**. Tracking issue and milestone: `v2.0.0`. Development branch: `2.0`.

djust 2.0 is defined by three default flips (explicit state exposure, strict event parameters, strict event security) and the deletions they unlock. Everything else is cleanup that 1.4 warns about first, as [API_STABILITY.md](../API_STABILITY.md) requires. Baseline: `main` at 1.3.0rc10, which has 245k lines of Python, 27.6k lines of client JS and 112.5k lines of Rust; the installed wheel is 38 MB.

Line references are from that commit, and sizes are approximate. Items marked *(unverified)* come from a read-only survey and need a repro or a second look before work starts.

## Direction settled (2026-10-19)

The owner settled the direction below. It is direction only: it approves no API, setting name, wire format or date. Where a section further down disagrees, this section wins and the older text is marked. The delivery sequence, acceptance matrix and the list of open questions are in [2.0-delivery-plan.md](2.0-delivery-plan.md).

1. **1.4 is the migration bridge.** 1.4 adds deprecation warnings, a migration guide and checker, and one combined opt-in for explicit exposure, strict event parameters and strict-only event security. 1.4 keeps today's defaults, imports and compatible behaviour. 2.0 makes those contracts mandatory and removes the legacy paths. There is no broad `djust.compat` mode at any point in 2.x.
2. **Actors go in a fixed order:** inventory downstream `use_actors` first, then the exposure changes, then removal of the Python actor integration, then removal of the Rust actor crate (`crates/djust_live/src/actors/`). Rust rendering and the VDOM stay, and so do the serialization and reserved-name safeguards that explicit rendering still needs ([2.0-exposure-flip.md](2.0-exposure-flip.md) §5 G1, G2).
3. **One transport-independent event, state and render core.** WebSocket, SSE and HTTP each fall back gracefully. Shared state and results outlive the connection that produced them; HTTP polls for updates when push is unavailable. Correctness must not depend on sticky sessions or on one shared Python view object.
4. **Pluggable shared storage**, with Redis, database and other implementations. 2.0 has restart-safe jobs: a separate, pluggable executor and durable named jobs with serializable inputs. Celery is a candidate adapter; it is not selected and not mandatory. The lifetime of local callbacks is defined separately. Uncertain outcomes are reconciled. There is no exactly-once guarantee for external effects and no blind replay.
5. **Floors and packaging.** The Python 3.12 / Django 5.2 floors for 2.0 are conditional on an inventory of dependent apps and a support-window check; 1.4's requirements are a separate question. Core stays one distribution with optional integrations and adapters. Splitting packages is deferred until a measured benefit exists.
6. **Retained features.** Lazy children and resumable uploads are ported to explicit, shared-state, HTTP-compatible designs. Arbitrary snapshot and private-attribute restoration, and executable debugger time travel, are removed. Declared reconnect and back-navigation state stays, with fresh authorization, and so does a redacted, read-only debug history.
7. **Release gates.** Each must pass before 2.0.0:
   - real apps migrate through 1.4;
   - retained features behave the same on every transport;
   - reconnects, node changes and worker restarts keep authorized state and durable results, with deduplication;
   - each removal has a replacement and a usage inventory first.

   Dates follow the evidence.

## 1. Default flips

ADR-036 and ADR-038 both say their legacy code is deleted "when a major release makes the new mode the default". 2.0 is that release.

| Flip | Today | What it lets 2.0 delete | Who it breaks |
| --- | --- | --- | --- |
| `exposure_policy` `legacy` → `explicit` (ADR-038 Step R) | `"legacy"`, `live_view.py:740`; `uses_legacy_exposure` has 102 call sites in 27 files | The reflective attribute walk; private-attribute persistence; `_FRAMEWORK_INTERNAL_ATTRS`; legacy session and signed-snapshot restore (`runtime.py:3622-3781`); the legacy save path; `security/state_snapshot.py`; `PersistentLiveView`; `enable_state_snapshot`; the legacy-only actor mode | Every app that relies on implicit public attributes as state. Needs a migration guide and a codemod. |
| `event_parameter_policy` `legacy` → `strict` (ADR-036 Step R) | `"legacy"`, `config.py:118` | `coerce_parameter_types`, `_coerce_value`, `_coerce_single_value`; the legacy client collectors and `_target` keys; the legacy branches of `checks/bindings.py` | Handlers that take untyped or extra parameters |
| `event_security`: remove `open` / `warn` | strict is already the default (`config.py:111-115`) | The two modes and their log path (`websocket_utils.py:140-163`) | Projects that set `open` or `warn` |

Defaults proposed to switch at the same time. These are proposals, not settled by the 2026-10-19 direction; each needs its own design and owner review:
- `hook_namespacing`: `lax` → `strict`.
- `DJUST_TENANTS['STRICT_MODE']`: removed, so isolation always fails closed.
- `DJUST_LIVE_RENDER_ALLOWED_MODULES`: defaults to the mount allow-list instead of permitting everything.

## 3. Simplifications

| Area | Today | Proposed for 2.0 | Effort |
| --- | --- | --- | --- |

## 4. Package split

> **Deferred (2026-10-19).** Core stays one distribution with optional integrations and adapters. The table below is kept as a survey; a split is reconsidered only with a measured install-size or dependency benefit. See *Direction settled*, item 5.

The optional extras make nothing optional today: `auth`, `tenants`, `theming`, `admin` and `deploy` are empty. Only a separate distribution can take code out of the base install.

| Subsystem | Proposal |
| --- | --- |
| LiveView runtime, component machinery, uploads, presence, push, `db` notifications, `auth/core` | Stay in core. Add a `postgres` extra for `djust.db`. |
| WebSocket stack (`channels`, `msgpack`) | Moves behind `djust[live]`, as decided in #2560, with a 1.x warning first |
| Components catalog (~52k lines, 2.2 MB static) | `djust-components`, on the same release train |
| Theming (~42k lines) | `djust-theming`; the theme-head hook stays in core |
| Accounts pages, social, allauth integration | `djust.contrib.accounts` behind an extra |
| MCP, observability, AI discovery, bug capture, `audit_*` | `djust-devtools`; only the DEBUG hooks stay in core |
| Deploy CLI | Moves to djustlive, which drops `click` and `requests` from the base install |
| Scaffolding | `djust-create`, per ADR-007 |
| `admin_ext` | Separate distribution, or deprecate |
| `clocks`, `audio`, the LiveView Native renderers | Move under `djust.experimental` |
| PWA, tutorials | Behind an extra, with their client JS made opt-in |

djust.org and djustlive import `djust.theming`, `djust.auth`, `djust.components.base`, `djust.db` and `push_to_view`, so every move needs a re-export path for one release. Add import-linter contracts so core cannot import the split packages (ADR-007 open question 6).

## 7. Sequence

1. **1.3.0 final and 1.3.x**: the survey bugs and the packaging quick wins.
2. **1.4, the deprecation release**: a `warn_deprecated` for everything 2.0 removes, and warnings for views on legacy exposure or legacy parameters. A codemod or `djust_audit --fix` for the exposure migration. The 2.0 migration guide as a draft. The combined strict opt-in (*Direction settled*, item 1). ~~The split distributions released alongside, with core re-exporting from them.~~ (Deferred 2026-10-19, item 5.)
3. **2.0 alphas, flips first** (proposed schedule; the 2026-10-19 direction settles only that 2.0.0 final has no legacy runtime, behind the inventory, replacement and migration gates):
   - Alpha 1 flips the three defaults. Raising the floors to Python 3.12 and Django 5.2 is conditional on the dependent-app inventory and support-window check (item 5).
   - Each later alpha runs one deletion stream: ADR-038 Step R, ADR-036 Step R, the transport core, the render frame, the component catalog.
   - djust.org and djustlive are tested against every alpha.
4. **2.0 release candidates**: re-exports removed, ~~the `djust.compat` shim in place~~ (superseded 2026-10-19: no broad compat mode), and the security audit re-run on the new transport core.
5. **2.0.0**, once the release gates in *Direction settled* item 7 pass; dates follow that evidence. 1.x gets security fixes for the support window the policy sets.

The detailed, dependency-ordered PR sequence is in [2.0-delivery-plan.md](2.0-delivery-plan.md) §1.

## 8. Open decisions (owner)

Status as of 2026-10-19. **Settled direction** means the owner chose the direction (*Direction settled* above); the API and details are still open unless stated. **Conditional** means agreed subject to a named check. **Open** means not decided. Only fully settled items are ticked.

- [x] Explicit exposure as the 2.0 default (ADR-038). **Settled direction**: mandatory in 2.0, with a 1.4 opt-in and warnings (item 1). Open: the 1.4 opt-in's API and precedence, production diagnostics and public-page caching.
- [x] Strict event parameters as the default (ADR-036), and removing `event_security` `open`/`warn`. **Settled direction**: mandatory in 2.0, part of the 1.4 combined opt-in (item 1). Open: the strict-mode setting name, scope and precedence against per-handler and per-view overrides.
- [ ] Python floor 3.12 and Django floor 5.2. **Conditional** on an inventory of dependent apps and a support-window check at the eventual release date (item 5). 1.4's requirements are reviewed separately. CI tests only Python 3.12–3.15 and Django 5.2; `pyproject.toml` still declares `requires-python = ">=3.11"` and `Django>=4.2.29,<6`; Django 4.2 LTS ended in April 2026.
- [x] Split distributions, or keep one wheel and only trim it. **Settled direction**: keep one core distribution with optional integrations and adapters; splitting is deferred until there is a measured benefit (item 5).
- [ ] One component system: Django tags rendered through the Rust bridge, after a benchmark. **Open.**
- [ ] Removing the Tokio actor system and the Rust component crate. **Settled direction for actors** (item 2: inventory, exposure changes, Python integration, then the Rust crate). Not ticked, because the Rust *component* crate is a separate question that remains **open**; part of it (`djust_components::python`, `ui`) is already gone (Work log).
- [ ] Moving the deploy CLI to djustlive. **Open.**
- [ ] A wire-protocol change (one render frame). **Open.** A shared core (item 3) does not approve the single-frame proposal.
- [ ] `@client_state`, `@optimistic`, `@cache`: implement or delete. **Open.**
- [ ] Target dates for 1.4 and 2.0. **Open.** Dates follow the release-gate evidence (item 7).
- [ ] New (2026-10-19): the shared storage and executor interfaces, adapter selection, retention, retries, leases and cancellation. **Open.** Direction only (item 4); see the ADR outline in [2.0-delivery-plan.md](2.0-delivery-plan.md) §5.
