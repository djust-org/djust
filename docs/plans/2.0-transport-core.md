# djust 2.0: one transport core (server)

Design for the server half of the "One transport core" and "One render frame"
rows in [the 2.0 plan](2.0.0-plan.md) §3. The client half has its own plan
(behaviour-neutral steps T1–T4 and owner decisions D1–D7); §5 maps those
decisions onto this design.
This document makes no code changes.

The survey was done on `origin/2.0` on 2026-10-17. Line numbers refer to that
tree and move as PRs land.

## 0. Summary

djust serves a LiveView over five server entry points. Only two of them go
through `ViewRuntime`, and those two do so through transport adapters large
enough to be second implementations. The target is one turn pipeline in
`ViewRuntime` with a thin adapter per wire. Side effects leave through one
outbound queue and reach the client as the `effects` of one render frame.
Server-originated turns (push, tick, db_notify) also run through the runtime,
so they work on every wire that can carry them.

## 2. Target

### 2.1 One turn pipeline

Every interaction is a **turn** on a mounted view. `ViewRuntime` gets one entry
point:

```text
runtime.run_turn(turn)            # turn: Mount | Event | UrlChange | Push | Tick | Notify | Call
  1. resolve owner (page view / slot / child)       — once
  2. authorize (view → handler → object; fresh for server-originated turns, ADR-038 D-l)
  3. validate parameters (ADR-036)                  — skipped for Push/Tick/Notify
  4. run the handler / hook under the tenant scope and diagnostic_scope()
  5. persist (exposure: explicit save / snapshot)
  6. render (unless skip-render or Call)
  7. drain the outbound queue  → effects
  8. emit ONE frame: transport.emit(frame)
  9. run deferred callbacks, then dispatch background work
```

`Call` is the API / server-function turn: no render, and the handler's return
value is the frame's payload.

### 2.2 Thin adapters

An adapter only knows its wire:

```text
class Wire(Protocol):
    session_id, client_ip, build_request()        # identity
    emit(frame)                                    # write one frame
    close(code)
    capabilities: {"push", "tick", "binary", "slots"}   # what the wire can carry
```

The behaviour now spread over the 24 `Transport` hooks becomes runtime code
keyed on capabilities: version stamping, actor dispatch (gone with the plan's
actor removal), recovery arming, and auth re-checks. The target is
`WSAdapter` at roughly 200 lines and `SSEAdapter` at roughly 150.

The HTTP POST fallback becomes an `HTTPAnswerAdapter` that collects the one
frame of the turn and returns it as the JSON response, which is what plan
decision D4 on the client side expects. The two API dispatchers become a
`CallAdapter` around a `Call` turn.

### 2.3 One render frame with `effects[]`

The mixins plan replaces the five side-channel queues (`_pending_push_events`,
`_pending_navigation`, `_pending_flash`, `_pending_page_metadata`,
`_pending_layout`) with one ordered `view._outbound` and one
`_drain_outbound()`. Step 7 of the pipeline drains it into the frame:

```json
{"type": "render",
 "target": "<view_id or null for the page>",
 "version": 12, "ref": 7, "source": "event",
 "patches": [...] | "html": "...",
 "effects": [{"kind": "push_event", "event": "...", "payload": {}},
             {"kind": "flash", ...}, {"kind": "page_metadata", ...},
             {"kind": "layout", "path": "...", "html": "..."},
             {"kind": "navigate", ...}],
 "async_pending": true}
```

- One frame per turn replaces `patch`, `html_update`, `noop`,
  `embedded_update` and the per-side-effect frames. A turn with no render and
  no effects still sends a frame, which is today's `noop`.
- `effects` are applied in the order the client receives them. The drain keeps
  today's canonical order (push events → flash → page metadata → layout →
  navigation) by sorting on kind rank, so the wire order of side effects does
  not change.
- `error` stays its own frame, built by the shared `build_error_frame`.
  `stream` and upload frames also stay separate, because they are not turn
  results.
- The HTTP answer is the same object, so `applyHttpSideChannels` disappears
  into the shared client dispatcher (client T1).

### 2.4 Server-originated turns on every wire

| Turn | Needs | WebSocket | SSE | HTTP-only |
| --- | --- | --- | --- | --- |
| Push (`push_to_view`) | A channel-layer subscription per session, and a turn runner | Has both today in the consumer; move the runner to the runtime | Add a per-session channel-layer receive task on the session's loop (`channel_layer.new_channel()`, `group_add` for the view's push groups, then `run_turn(Push)`) | No persistent channel. Recommend unsupported, with a startup or system-check warning for views that declare push groups and can be served HTTP-only |
| Tick | A periodic task per mounted view | `_run_tick` in the consumer; move it to the runtime | The same runtime task on the session loop, stopped at session shutdown | Unsupported (as above) |
| `db_notify` | Subscription to the notify group, and a turn runner | Consumer; move to the runtime | The same channel-layer receive task as push | Unsupported |
| Background work | A task runner, and a way to deliver the result frame | Runtime and consumer twins; keep the runtime one | Runtime (already) | Run the tasks, but the result has no path to the client. Options: (a) run them inline before answering, (b) refuse `start_async` on HTTP with a clear error, (c) unsupported with a warning. **Owner decision.** |

The channel-layer subscription for SSE sessions is the only new mechanism. It
reuses the group names the consumer already joins, so `push_to_view` and
`notify_on_save` need no change.

## 3. What gets deleted

- Consumer twins: the seven `_flush_*` methods and `_flush_all_pending`, the
  async-work pair (≈320 lines), the server-push runner and its offloaded twin
  (≈250), the tick runner (≈230), and `_db_notify_to_view` (≈150). These move
  into the runtime once and are deleted from the consumer.
- `mixins/request.py` `post()` and its helpers (≈600 lines), replaced by
  `HTTPAnswerAdapter`.
- The duplicated auth and validation in `api/dispatch.py` (≈300 of its 683
  lines), replaced by the `Call` turn.
- `sse._flush_deferred_to_sse`.
- Most of the 24 `Transport` hooks.
- On the client, after the frame change: the per-side-effect `case`s and
  `applyHttpSideChannels`.

The total is roughly 3–4k lines of Python *(estimate)*.

## 5. Agreement with the client plan

The client plan's decisions, and how this design answers each:

- **D1, SSE `mount` parity** (inserted scripts, form recovery, sticky
  reattach, SW cache write, rAF deferral, `upload_configs`). These are client
  behaviours on a mount frame both wires already send. The server needs no
  change except `upload_configs`, which the runtime should include on every
  wire (part of TC9). The design agrees with the client recommendation: yes,
  one item per PR.
- **D2, hook `pushEvent` with a `ref`.** The runtime already echoes `ref` on
  turn results. With D2, every client event carries a `ref`, so the `render`
  frame can make `ref` required and drop the no-ref acknowledgement guess.
  This design assumes D2 is yes.
- **D3, one `djust:error` detail.** The server half is `build_error_frame`
  (#3542) on every wire, including HTTP (TC2). `event` and
  `validation_details` should come from the frame on every wire, and
  `recoverable: false` should mean the same thing on SSE. This design
  recommends yes, after TC2.
- **D4, a real `LiveViewHTTP` transport.** It pairs with TC7: the server
  answers an HTTP event with the same `render` frame, so the client class only
  needs `send` and `emit`. This design recommends doing both in the 2.0 alphas
  together.
- **D5, wire changes wait for the server design.** Agreed. The wire-changing
  steps are TC3 (`request_html` on SSE), TC5 (push, tick and db_notify frames
  on SSE) and TC9 (the `render` frame). TC9 is the only breaking frame change,
  and it lands together with the client.
- **D7, one liveness predicate.** With capabilities on the server, the client
  can ask the narrower question ("can this transport carry X?") instead of
  "is it live?". This needs no server work.

## 6. Open questions for the owner

1. **The frame change.** One `render` frame with `effects[]` (TC9) is a wire
   break. Old cached client bundles would need a forced reload. Is that
   acceptable in 2.0, given the client ships with its server?
2. **HTTP-only and server-originated turns.** Should push, tick and db_notify
   be declared unsupported on HTTP-only, with a warning, or should 2.0 add a
   long-poll answer?
3. **Background work over HTTP.** Should it run inline, be refused, or be
   unsupported with a warning (§2.4)? Today it is silently dropped.
4. **SSE subscriptions.** Is a channel-layer receive task per SSE session
   acceptable? It costs one channel per session, as the WebSocket consumer
   already has.
5. **API dispatchers.** Should they join the runtime as `Call` turns (TC8), or
   stay separate because they never render?
6. **Ordering against the exposure flip.** Should TC4 and TC7 wait for flip
   PRs 4 and 6 (this document), or land first and make the flip PRs rebase?
