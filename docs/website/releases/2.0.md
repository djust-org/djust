# Why djust 2.0

*November 2026 · 2.0.0rc6 is the current release candidate*

djust 2.0 is the release where the safe way and the fast way became the only
way. A LiveView still looks like the Django code you already write, but in 2.0
nothing leaves the server unless you declared it, every event argument is
typed before your handler sees it, and a typical turn does a fraction of the
work it did in 1.x.

```bash
pip install --pre djust    # 2.0.0rc6; a plain `pip install djust` still installs 1.3.x
```

Already on 1.3? Jump to [Upgrading](#upgrading-from-13). The short version:
do the work on 1.3.x, where both 2.0 contracts already exist as opt-ins, and
let `djust_exposure_inventory --fix` make the mechanical changes.

## 2.0 at a glance

| | What you get |
| --- | --- |
| **Secure by default** | Only declared state reaches the template, the session or the browser. Event arguments are typed and checked. A strict Content-Security-Policy works without `'unsafe-inline'`. |
| **Faster** | A one-cell change in a 1,000-row table takes about 7 to 9 ms of server time (p50) on the project's benchmark, down from about 17 to 22 ms at the start of the last release candidate. A connected view holds about a third less memory. |
| **The same on every transport** | WebSocket, Server-Sent Events and the stateless HTTP fallback run the same checks and features, and the HTTP fallback now answers with patches instead of the whole page. |
| **State that survives** | Saved state goes to a store you choose, including a built-in encrypted one. Reconnects, uploads and background work pick up where they left off. |
| **Tools that tell you** | `djust_exposure_inventory --fix` does the mechanical upgrade, system checks name what still needs a person, and test helpers show exactly what a view renders and saves. |

## Secure by default

In 1.x, every public attribute you set on `self` became template context and
was copied into the session and the client state. That was convenient, and it
was also how a password hash or an internal flag could end up somewhere you did
not expect. In 2.0, a view says what each value is for.

```python
from djust import LiveView, state
from djust.decorators import event_handler


class InboxView(LiveView):
    template = """<div dj-root>
        <input name="q" dj-input="search">
        <button dj-click="open" dj-value-message-id="42">Open</button>
        <p>{{ query }} / {{ selected }}</p>
    </div>"""

    query = state("")                       # renders; stays on the server
    selected = state(0, persist="server")   # also survives a reconnect

    @event_handler()
    def search(self, value: str):
        self.query = value

    @event_handler()
    def open(self, message_id: int):
        self.selected = message_id          # already an int, already checked
```

**Explicit exposure is the only behaviour.** A field declared with `state()`
renders; anything else the template needs comes from `get_context_data()`.
Only `state(..., persist="server")` fields go into the session, and only
`client=True` fields reach the browser as raw data. Everything else stays on
the view object in server memory, where your handlers can read it and nothing
exports it. Models and QuerySets reach the renderer reduced to the fields the
template actually reads. See [Explicit exposure](../state/explicit-exposure.md).

**Strict, typed event parameters.** A handler's annotations are its contract:
`str`, `int`, `float`, `bool`, `Decimal`, `UUID`, `date`, `Optional[T]`,
`list[T]`, `dict[str, T]` and `Any`. An argument the handler did not declare,
or one that does not convert, is refused before your code runs, and the
refusal names the rule that failed. See
[Typed event parameters](../core-concepts/events.md#typed-event-parameters-strict-policy).

**Bindings and permissions follow what was rendered.**

- `dj-model` accepts only fields bound in the branch of the template that
  actually rendered for the current state, not every `dj-model` anywhere in
  the source. System check `djust.T030` lists the fields that need
  `allowed_model_fields`.
- Events routed to a LiveComponent or an embedded child view run the page
  view's object-permission check (`get_object()` / `has_object_permission()`)
  on every transport.
- The HTTP API and `@server_function` endpoints answer a `PermissionDenied`
  with a fixed message instead of the exception's text.

**A strict Content-Security-Policy, without `'unsafe-inline'`.** The scripts
djust loads carry the request's CSP nonce, constant inline styles became
attributes or classes, and `LIVEVIEW_CONFIG["csp_strict"]` replaces the
remaining inline styles and `on*=` handlers with markup a static module
handles. See [Security](../advanced/security.md).

**Escaping you do not have to think about.** A value marked safe for text is
always escaped when it is written into an attribute, in templates, components
and djust's own admin, auth and gallery templates. A static guard over
djust's source checks every `mark_safe` call site for the escaper its position
needs.

**Smaller things that add up.**

- Saved view state can be encrypted at rest with
  `djust.state_store.SealedSessionViewStateStore` (AES-256-GCM, keys you
  supply and rotate).
- Password values are kept out of drafts, form recovery and the
  `dj-auto-recover` envelope.
- Presence identifies an anonymous user by an opaque id instead of the
  session key.
- The template engine's date and timezone code moved from `chrono` and
  `chrono-tz`, which RustSec marks unmaintained, to `jiff`, with the IANA
  timezone database bundled.

## Faster where it counts

Performance work in 2.0 was driven by benchmarks that run complete turns
through the real stack (`make benchmark-transports`, and
`make benchmark-client-turns` for the browser side). Every number below comes
from those benchmarks or from the measurement in the linked change; the method
and raw data are in
[the turn-transports baseline](../../performance/turn-transports-baseline.md).

| Measurement | Before | 2.0 |
| --- | ---: | ---: |
| One changed cell in a 1,000-row table, server turn p50 over WebSocket (8.8 to 10.4 ms with the session save) | 16.8 to 22 ms | **7.2 to 8.8 ms** |
| The same change, Rust render and diff alone | 3.4 ms | **1.6 ms** |
| Memory per connected view, 1,000-row table ([#3998](https://github.com/djust-org/djust/issues/3998)) | 7.3 MB | **5.2 MB** |
| Memory per connected view, ~100 KB table with 880 rows in state ([#4319](https://github.com/djust-org/djust/issues/4319)) | 4.19 MB | **2.69 MB** |
| HTTP fallback answer, one changed cell in a 100-row table ([#4108](https://github.com/djust-org/djust/issues/4108)) | 28,971 bytes | **134 bytes** |

The turn figures are from different machines: about 22 ms is the start of
rc6 on the original benchmark machine, and 16.8 ms is the same code on the
slower machine where the final 7.2 to 8.8 ms was measured. The memory rows are
two separate cuts on two different table shapes, so they are not additive.

Where that comes from:

- **Only changed rows re-render.** Rust keeps each item's HTML of an outermost
  `{% for %}` and reuses it when the item has not changed, including rows that
  hold a nested loop. A handler that changes a few rows of a long list sends
  Rust only those rows.
- **Change detection is native.** A container of plain data is digested in
  Rust instead of building and hashing a Python fingerprint tree, and a
  connected view keeps a 16-byte digest per attribute instead of two
  fingerprint trees.
- **Text changes skip the parse.** A render that differs only in the text of
  a few nodes rewrites them in place instead of parsing and diffing the page.
- **Turns answer before the save.** Over WebSocket and SSE, a turn's reply is
  sent first and its state reaches storage within
  `DJUST_STATE_SAVE_INTERVAL` (2 seconds by default). See
  [Save frequency](../state/save-frequency.md).
- **Less client JavaScript up front.** The page loads a core runtime of
  about 68 KB gzipped <!-- size-claim: core --> and fetches uploads, virtual
  lists, transitions, dialogs, component widgets and other features only on
  pages that use them, preloading what the first render needs. After a patch,
  rescans and hook updates touch only what changed. See
  [Client bundle](../guides/client-bundle.md).
- **Partial renders and mounts do less.** `set_changed_keys()` sends a diff,
  a wrapper `{% if %}` or `{% block %}` reuses its unchanged children, and a
  live mount skips re-rendering a page shell that holds no child view.

## The same on every transport

djust serves a page over WebSocket, over Server-Sent Events, or over plain
HTTP POSTs for networks where neither works. In 2.0 they behave the same:

- **The HTTP fallback answers with patches.** Each answer carries an HMAC
  of the render, and the client compares the shape of its own DOM with the
  server's, so a patch is only ever applied to the page it was computed for.
  Anything else gets the whole page, as before. See
  [HTTP-only mode](../guides/http-only-mode.md).
- **Children and lazy views work everywhere.** Embedded `{% live_render %}`
  children, `dj-lazy` containers and sticky children take events over the
  HTTP fallback and SSE with the same ownership, schema and permission checks
  as the socket.
- **Streams and pushes reach SSE clients.** `stream_to`, `stream_text`,
  `push_state()` and friends no longer need a WebSocket.
- **A versioned wire protocol.** One `render` frame per turn, with
  `effects[]`, and a protocol version on every request. A tab still running
  an old cached client reloads itself once instead of misbehaving after a
  deploy.
- **Slow clients cannot pile up memory.** Outbound frames are buffered up to
  `max_outbound_buffer_bytes` (4 MiB by default); past it the client
  reconnects and resyncs through the ordinary recovery path.

## State that survives

- **Pluggable state storage.** `DJUST_STATE_STORE` names where saved view
  state lives: the Django session by default, the built-in sealed store, or
  your own `ViewStateStore`. djust keeps every check on the envelope (session,
  user, tenant, route, tab, expiry, size), so a store that returns the wrong
  bytes yields a fresh `mount()`, never someone else's state. See
  [State store](../state/state-store.md).
- **Honest reconnects.** A reconnect that can only restore an older state than
  the page showed says so ("Your most recent changes could not be restored.")
  instead of silently rolling back. See
  [What survives](../guides/state-survival.md).
- **Uploads resume.** An upload in flight resumes after a WebSocket
  reconnect, bound to the same session, user, tenant and page.
  `allow_upload(timeout=...)` and view-level upload hooks
  (`handle_upload_started` and friends) are new. See
  [Uploads](../guides/uploads.md).
- **Background work that must finish, finishes.**
  `start_async(..., survive_disconnect=True)` and
  `@background(survive_disconnect=True)` run to completion after the user
  leaves.
- **Sticky children keep their state.** `sticky_update_inputs` lets a sticky
  child accept changed inputs, across `live_redirect` too, without being
  remounted. See [Sticky child persistence](../guides/sticky-child-persistence.md).

## Better building blocks

- **A JavaScript widget contract.** The `dj-hook` lifecycle is specified
  (one instance per element, `mounted()` and `destroyed()` exactly once), along
  with what a widget owns, how props reach it, focus and IME across updates,
  and strict-CSP rules. `this.pushEvent(..., {outcome: true})` tells a hook
  whether its event succeeded, was refused, rate-limited or cancelled. See
  [Hooks](../guides/hooks.md).
- **One renderer per component.** The `djust.components.ui` components and
  many component tags (`data_table`, `badge`, `pagination`, `accordion`,
  `sidebar`, `toolbar` and more) draw the same markup on Django's template
  engine and on the Rust engine, with accessibility fixes found along the way.
- **Current platforms.** Django 4.2 through 6.1, Python 3.11 and newer.

## Tools that tell you

- **`manage.py djust_exposure_inventory --fix`** makes the mechanical upgrade
  changes and lists what needs a person. `--dry-run` shows the diff first.
- **System checks for every upgrade step**, such as `djust.T027` (a template
  name the view never supplies), `djust.V033` (a handler strict parameters
  would refuse) and `djust.T030` (a `dj-model` field that needs an allowlist).
- **Fail loudly in tests.** `DJUST_UNSUPPLIED_NAMES = "error"` turns a template
  name that would render blank into an error.
  `djust.testing.rendered_state(view)` and `persisted_state(view)` show exactly
  what a view handed the template and what it would save. See
  [Testing](../guides/testing.md).
- **A rendered-page accessibility audit.** `djust_audit --a11y --url` runs
  axe-core over real pages in headless Chromium, for the contrast, landmark and
  heading checks a template scan cannot do. See
  [djust audit](../guides/djust-audit.md).
- **Production diagnostics.** `LIVEVIEW_CONFIG["log_exception_detail"] = True`
  keeps tracebacks in your server logs and reports exceptions to Sentry on
  every transport, while clients still see a generic error.

## Less to carry

2.0 removes what made djust harder to reason about: the legacy exposure and
parameter modes and every code path behind them, the 1.x compatibility shims,
the pure-Python fallbacks for a missing Rust extension, the experimental actor
system, the React integration, time-travel debugging, and deprecations going
back to 0.x. There is now one way to do each of these things, and it is the
one the docs teach.

## Upgrading from 1.3

2.0 is a major release, and some of it will need your attention. Here is what
to expect.

**What changes for most apps**

- A public attribute set on `self` no longer renders. Declare it with
  `state()` or return it from `get_context_data()`; `{{ items_count }}`
  becomes `{{ items|length }}`.
- Event handlers need annotated parameters, and event arguments are passed as
  `dj-value-*` attributes instead of `data-*`.
- `exposure_policy = "legacy"` and `parameter_policy="legacy"` raise
  `ImproperlyConfigured` naming the replacement.
- Saved state is limited to `state(..., persist=...)` fields;
  `enable_state_snapshot` and `PersistentLiveView` are gone.
- Several component tags and `djust.components.ui` components render
  different HTML, so check custom CSS and template overrides that target them.
- The wire protocol changed; open tabs reload once after you deploy.

**How to do it**

1. Upgrade to the newest 1.3.x first. Both new contracts exist there as
   opt-ins, so you can migrate one view at a time and deploy between steps.
2. In a scratch environment with `pip install --pre djust`, run
   `python manage.py check` and
   `python manage.py djust_exposure_inventory --fix --dry-run`.
3. Apply `--fix`, work through its "Needs a person" list, and compare each
   page's HTML with a copy saved before you started.

Actors, whole-view state snapshots, time-travel debugging and the React
integration have no replacement; the guide says what to use instead.

The full, step-by-step guide, with every removed name, the check that reports
it and whether `--fix` rewrites it, is
[Migrating to djust 2.0](../guides/migrating-to-2.0.md). Every change is
listed in the [changelog](https://github.com/djust-org/djust/blob/main/CHANGELOG.md).
