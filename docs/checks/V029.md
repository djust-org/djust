### V029 — a handler changes a value a later event reads, and the value is not saved
- **Severity**: Warning
- **Method**: Runtime (class inspection and the handlers' source). It builds one bare `LiveView()` to list djust's own instance attributes; no application view is constructed.
- **What it detects**: an `@event_handler` or `@action` of an explicit view that changes a value djust does not save between requests, when a later event reads that value. A view's public attributes and `state()` fields are saved server-side automatically; two things are not: an attribute whose name starts with an underscore (`self._page += 1`), and a `state()` field declared `persist=False` that a handler reads and then changes. A later event reads the value when the handler reads the old value before changing it (`self._count += 1`, `self._x = f(self._x)`, `self._items.append(...)`), or when another handler or `get_context_data()` reads it. Such a value answers every HTTP-fallback event, and the first event after a reconnect, from its `mount()` value, with no error; within one WebSocket connection it is kept. Not reported: public attributes and `state()` fields without `persist=False` (they are saved), a value a handler recomputes from its own arguments and only it reads, keys of `temporary_assigns`, djust's own attributes (every name in `djust._exposure.reserved_state_names()`, and any name a djust class in the view's MRO defines), descriptors other than `state()` (a property, `@computed`), and legacy views. A value that is public but cannot be saved (a model instance, a `Decimal`) is not found by this check: the `djust.automatic_state` logger names it at run time. Only the handlers' own bodies are read: a change in a helper the handler calls, or through `setattr()`, is not reported. Reported once per class and attribute, on the class whose handler changes it.
- **Fix**: rename the attribute without the leading underscore (saving a value does not render it), or remove `persist=False`; or rebuild the value in `mount()` / `handle_restore()` so that no later event depends on the old one.
- **Suppression**: `DJUST_CONFIG = {"suppress_checks": ["V029"]}` or `SILENCED_SYSTEM_CHECKS = ["djust.V029"]`

### V029: a handler changes a value a later event reads, and the value is not saved

**Severity**: Warning

**What causes it**: An event handler of an explicit view changes `self._page` (`self._page += 1`, `self._items.append(...)`, or a value another handler or `get_context_data()` reads). A name with a leading underscore is not saved between requests, so on the HTTP fallback, where each event mounts a new view, and after a reconnect, the change is lost; within one WebSocket connection it is kept. The same is reported for a `state()` field declared `persist=False`. Message: "<view> next_page() changes self._page, which a later event reads, but a name with a leading underscore is not saved: on the HTTP fallback and after a reconnect the change is lost (within one WebSocket connection it is kept)."

**Fix**: Rename it without the underscore: `self.page`. Public attributes are saved server-side and are not rendered unless declared. Suppress with `DJUST_CONFIG = {"suppress_checks": ["V029"]}`.
