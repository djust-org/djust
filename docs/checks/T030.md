### T030 — `dj-model` inside a custom block tag body
- **Severity**: Warning
- **Method**: Template scan (each template file's tags, in order).
- **What it detects**: a `dj-model="<field>"` binding in the body of a block tag other than Django's control-flow and structural tags (`if`, `for`, `with`, `block`, `autoescape`, `spaceless`, `filter`, `partialdef` and the locale/time-zone scope tags). The view's dj-model write allowlist holds only the bindings the last render emitted from template text, and the body of a custom block tag (`{% ifperm %}…{% endifperm %}`, `{% ifchanged %}`, a library block tag) never counts, because the tag decides what of its body reaches the page. A Rust block-tag handler that declares `EMITS_BODY = True` (djust's `app_shell`, `app_sidebar`, `app_header` and `app_content` do) is exempt.
- **Fix**: list the field in the view's `allowed_model_fields`, or move the input out of the tag.
- **Suppression**: `DJUST_CONFIG = {"suppress_checks": ["T030"]}` or `SILENCED_SYSTEM_CHECKS = ["djust.T030"]`

### T030: `dj-model` inside a custom block tag body

**Severity**: Warning

**What causes it**: a `dj-model="<field>"` binding in the body of a custom block tag. The tag decides what of its body reaches the page (a permission-gate tag may drop it), so the binding is not added to the view's dj-model write allowlist, and a client update of that field is refused. Message: '<file>:<line> -- dj-model="note" is inside the body of {% ifperm %}; it is not writable unless listed in allowed_model_fields.'

**Fix**: add the field to the view's `allowed_model_fields` (the view then accepts it whatever the tag renders), or move the input out of the tag. A Rust block-tag handler that always emits its body unchanged can declare `EMITS_BODY = True`. Suppress with `DJUST_CONFIG = {"suppress_checks": ["T030"]}`.
