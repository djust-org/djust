# ADR-037 D2/D3: executable documentation, generators and final acceptance

Date: 2026-09-25
Status: approved design, awaiting spec review
ADR: [ADR-037](../../adr/037-event-contract-checks-and-executable-documentation.md);
tracker: `docs/adr/component-conventions-implementation.md`, "ADR-037 — checks and
executable documentation" (D1 built; D2, D3 and DR open).

## Intent

ADRs 034–037 shipped in 1.3.0rc3 (#3122). What remains:

- **D2.** Documentation examples become fixtures the test suite executes. Each
  test layer is shown to fail when its gate is removed.
- **D3.** Final acceptance on delivered documentation, not repository Markdown.
  Then change the ADR statuses.
- **DR.** Check it off. #3122 was the deletion PR for every `RETIRE` row, and it
  merged on 2026-09-25.

**Owner decisions (2026-09-25):**

1. **Scope: the ADR surface plus drift.** The covered sections are the ADR
   034–037 guides and AI references, generator output and the catalogue entry.
   Every Python block in them is executed or skipped with a stated reason. The
   other ~600 Python blocks in `docs/website/` keep today's parse/import check
   (`scripts/check-doc-snippets.py`) and are reported as unexecuted.
2. **Delivery: staged 1.3 docs.** D3 verifies a djust-docs build pinned to a
   1.3 release candidate. Production docs.djust.org stays on stable 1.2.x until
   1.3.0 final. The ADRs become "Accepted — delivery verified on staged 1.3
   docs". Production delivery is a 1.3.0 release gate.
3. **Harness shape: Markdown markers** (approach A). Rejected: a central
   registry (B), which cannot see an example added under an unregistered
   heading; and example source files included into Markdown (C), which needs
   include support in both docs renderers.

## 1. Shared harness and drift check

### Current state

Three tests execute documented examples, one per ADR. Together they are 566
lines:

- `test_adr034_documented_examples.py`
- `test_adr035_documented_examples.py`
- `test_adr036_documented_examples.py`

Each re-implements the same four pieces:

- the snippet-checker extractor;
- section-scoped pairing of each Python block with the `html` block after it;
- loading the Python block as a module;
- a page driver: a real GET, then events through the real HTTP fallback, using
  the identities the page rendered.

Only their scenarios differ.

### Design

**`python/djust/tests/_doc_examples.py`** is the one harness:

- `blocks(path)` returns every fenced block, its language, its line, and the
  marker that precedes it (if any). It uses `scripts/check-doc-snippets.py`'s
  extractor, so both tools see the same blocks.
- `Example` records the id, the scenario, the source file and line, the Python
  code and the paired template.
- `load(example)` executes the block as a uniquely named module, so no example
  can shadow another. It returns the view class.
- `Page` does a real GET and drives events through the real HTTP fallback. It
  is lifted from the ADR-034 test, and the other two tests switch to it.
- `COVERED` lists the covered sections as `(path, heading)`:
  - `docs/website/guides/interactive-components.md` (whole file);
  - `docs/ai/components.md`, "## Interactive components (djust 1.3+)";
  - `docs/website/guides/forms.md`, "## Editing one record with `ModelFormMixin`";
  - `docs/ai/forms.md`, "## ModelFormMixin: edit one record (djust 1.3+)";
  - `docs/website/core-concepts/events.md`, "## Typed event parameters (strict
    policy)";
  - `docs/ai/events.md` (the same section);
  - `docs/website/guides/error-codes.md`, the T019–T022 entries.

**Markers.** An HTML comment on the line before a Python block. Both docs
renderers hide it, as they already hide `<!-- doc-snippet-check: skip -->`:

```markdown
<!-- djust-example: dropdown-basic scenario=select-item -->
<!-- djust-example: skip -- fragment of the example above -->
```

**Scenarios** live in `python/djust/tests/doc_scenarios/`, one module per ADR.
Each module registers named functions:

```python
@scenario("select-item")
def _(page, example): ...
```

The three existing tests become these modules. Their assertions are kept
verbatim, so coverage does not regress.

**`test_doc_examples.py`** runs one parametrized case per marked, non-skipped
block. Its case ids are the marker ids.

**`test_doc_example_drift.py`** fails when:

- a Python block in a covered section has no marker;
- a marker names an unregistered scenario;
- a `skip` marker has an empty reason;
- a marker is not followed by a Python block;
- two markers share an id;
- a covered section's heading no longer exists. A renamed heading must not
  silently shrink coverage.

**Report.** `python scripts/doc-examples-report.py` prints executed,
skipped-with-reason and unexecuted counts for each covered file. The totals for
`docs/website/` as a whole are unexecuted but parse-checked. The drift test
asserts the report's covered totals, deriving them rather than restating them
(canon #2727).

**Gate-offs.** Each layer gets one mutation, recorded with its red output in
`docs/adr/notes/037-d2-gate-offs.md`:

| Layer | Mutation | Expected red |
|---|---|---|
| Extractor | drop the last block of each file | the drift test's "marker not followed by a Python block" |
| Pairing | pair each Python block with the previous `html` block | scenario tests |
| Scenario driving | make `Page.event` send nothing | scenario tests |
| Drift | treat every block as marked | the drift test's negative fixtures |

The harness asserts that each mutation applied and that the module still
imports. A `HUNG` or `ERROR` result is reported as an error, never as a pass
(canon #2129/#2135).

## 2. Generators, catalogue and djust-docs

Each generator's output is an `Example` the harness executes. It gets no
separate one-off test.

- **`python/djust/schema.py`.**
  - The `"forms"` pattern is rewritten as two examples: a `FormMixin` create form
    and a `ModelFormMixin` edit view. The edit view uses `get_object()` and
    `has_object_permission()`, not `_model_instance` in `mount()`.
  - `OPTIONAL_MIXINS` gains a `ModelFormMixin` entry.
  - A test executes both schema examples with a stand-in model, using the
    ADR-035 scenario.
- **MCP `scaffold_view`** (`python/djust/mcp/server.py:1384`). A new feature,
  `form_edit`, emits a `ModelFormMixin` edit view; `form` is unchanged. A test
  generates the code for each feature combination that includes `form` or
  `form_edit`, executes it, and drives the ADR-035 scenario.
- **Catalogue** (`python/djust/theming/gallery/catalogue.py`, the
  `usage_with_events` and `_usage_snippet` generators):
  - It gains an interactive `DropdownMenu` entry, in two variants: a single menu,
    and a keyed collection (C4-Q3).
  - The generated usage runs through the harness with the ADR-034 scenarios.
  - A browser pass on the local catalogue checks that two menus on one page open,
    select and close independently, and that a handler error is visible.
    Evidence goes in the ADR notes.
- **djust-docs** (a separate PR in `djust-org/djust-docs`).
  - `docs_verify.py:56`'s `_DECORATOR_RE` stops at the first dot, so
    `@menu.on.selected` reads as `@menu` and is reported as unknown.
  - A second pattern will recognise `@<name>.on.<event>` and accept it when
    `<name>` is assigned in the same block.
  - Positive and negative test cases are added. `make docs-verify` must pass.

## 3. D3: final acceptance

1. At the final revision, re-run each ADR's acceptance matrix (034, 035, 036 and
   037) and record the results in the tracker.
2. Complete the migration and AI guidance:
   - `docs/ai/` covers each ADR's patterns and its upgrade notes, which match the
     1.3.0rc3 CHANGELOG notes;
   - the generators (section 2) emit the same patterns.
3. **Staged delivery.**
   - Build djust-docs pinned to the latest 1.3 release candidate, locally or on a
     staging hostname.
   - Run `make docs-verify` on it.
   - Browse every page the ADRs added or changed. Record the URLs and the result.
   - Production is not changed.
4. Record the remaining static-analysis limits, for example dynamic bindings,
   non-constant includes and templates outside the scan.
5. Check off DR, citing #3122.
6. Set ADRs 034–037 to "Accepted — delivery verified on staged 1.3 docs", with
   the production gate stated as "docs.djust.org bumped with 1.3.0". The
   tracker's D2, D3 and DR boxes are checked with evidence.

## Delivery

- **djust PR 1 (D2):** the harness, drift check and report, the scenario modules,
  the generator changes, the catalogue entry and the gate-off notes.
- **djust-docs PR:** the decorator pattern.
- **djust PR 2 (D3):** the acceptance records, guidance, statuses and tracker.
  This lands after the staged delivery has been verified.

## Testing and success criteria

- The three existing documented-example tests pass as scenario modules, with
  their assertions unchanged. The first harness commit runs them side by side,
  and the old files are removed once the new ones pass.
- Every Python block in the covered sections is executed, or skipped with a
  reason.
- The drift test fails on each of its negative fixtures.
- Each gate-off turns red, and the notes record that output.
- Both schema examples, every MCP `form` / `form_edit` output and the catalogue
  `DropdownMenu` usage execute and pass their scenario.
- The full suite passes across every test root. So do `make docs-verify` in
  djust-docs and the staged browser pass.

## Out of scope

- Executing the other ~600 `docs/website/` Python blocks.
- Changing production docs.djust.org before 1.3.0 final.
- #3104 (over HTTP-only, embedded-child events reach the root view) and #3103
  (`get_debug_info()` crashes on a property that raises something other than
  `AttributeError`). Both are tracked separately.
- #3130 (the exposure-test timing flake).
