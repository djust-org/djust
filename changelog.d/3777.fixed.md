- **`{% for g in u.groups.all %}{{ g.name }}{% endfor %}` over a QuerySet renders the related rows on a LiveView and under `DjustTemplateBackend`, as Django and `_rust.render_template` do (#3777).** The Rust queryset serializer (`serialize_object_with_paths` in `crates/djust_live/src/lib.rs`) walked the extracted paths `groups.all` / `groups.all.name` with `getattr`: `groups` is the related manager and `all` is its *bound method*, which has no `name`, so it shipped `{"groups": {"all": {}}}` and the loop ran over an empty dict. The Python codegen twin (`python/djust/optimization/codegen.py`) has always iterated `.all()`; the Rust one never did, and the key-count fallback to that codegen cannot fire because the `groups` key is present. Only a QuerySet was affected, so a `list[Model]` of the same rows rendered the names. Three sibling spellings of the same missing step were wrong too and are fixed with it: `{{ u.groups.all|length }}` counted the characters of the QuerySet's `repr` (41 for a two-row relation), `{% if u.groups.all %}` was true for an *empty* relation, and `u.groups.all.0.name` was empty. A called `all` still goes through the one `template_call_guard` (#3772), so a related manager whose `all` is marked `alters_data` or `do_not_call_in_templates` is never run. Pinned through `DjustTemplateBackend`, a LiveView's HTTP GET, its WebSocket mount and the serializer itself, with Django's engine as the control and real `User` / `Group` rows (`python/tests/test_queryset_all_traversal_3777.py`).
