- **A handler whose only effect is a stream call now reaches the page, and `temporary_assigns` rows under `dj-update="append"` / `"prepend"` are added after the rows already there** — over a WebSocket or SSE, a handler that only called `stream_insert` / `stream_delete` / `stream_prune` / `stream_reset` (or `stream()` with items) was answered with a `noop`, so the row waited for the next unrelated render; the same handler as a tick did not send a frame. `_snapshot_assigns`, the one comparison every skip decision uses, now sees a stream mutation (a `_stream_epoch` bumped only when a stream actually changed), while an event that touches no stream, a prune above the current size or a delete that matches no row stays a `noop`. And on a view with `temporary_assigns`, `self.rows = [new_row]` next to another change replied with a patch that had no row (the key was always left out of the changed keys), while as the only change it rewrote the first stored row and removed the rest, because the differ had no `dj-update` handling (only the client's full-HTML path did). The key now counts as changed once it holds anything but its reset default, and the differ keeps a `dj-update` container's stored children and adds the new ones by `id` (`splice_accumulating_subtrees`, switched on by the new `set_accumulate_updates` for views that declare `temporary_assigns`), so the patch is an `InsertChild` per new row. A view without `temporary_assigns` is unchanged. `prepend` is correct but not minimal: stored rows shift down by position. (#3639)
