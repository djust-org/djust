- **A handler whose only effect is a stream call now reaches the page, and `temporary_assigns` rows under `dj-update="append"` / `"prepend"` are added after the rows already there** — over a WebSocket or SSE, a handler that only called `stream_insert` / `stream_delete` / `stream_prune` / `stream_reset` (or `stream()` with items) was answered with a `noop`, so the row waited for the next unrelated render; the same handler as a tick did not send a frame. `_snapshot_assigns`, the one comparison every skip decision uses, now sees a stream mutation (a `_stream_epoch` bumped only when a stream actually changed), while an event that touches no stream, a prune above the current size, a delete that matches no row or a reset of an empty stream stays a `noop`. And on a view with `temporary_assigns`, `self.rows = [new_row]` next to another change replied with a patch that had no row (the key was always left out of the changed keys), while as the only change it rewrote the first stored row and removed the rest, because the differ had no `dj-update` handling (only the client's full-HTML path did). The key now counts as changed once it holds anything but its reset default, and the differ keeps a `dj-update` container's stored children and adds the new ones by `id` (`splice_accumulating_subtrees`). Only a container whose body reads a `temporary_assigns` key (or `streams`, or an `{% include %}`) accumulates, found in the stored tree by its `id` and not by position; any other `dj-update` list, including one in a view that declares `temporary_assigns`, is re-rendered whole as before. `prepend` is one insert at the front per event with each row keeping its own `id`, attributes and `dj-id`. **Behaviour notes:** an accumulating container's rows stay in the server's copy of the page, so the stored tree grows with every row added and each event costs a little more (about 1 ms with 200 rows, 15 ms with 8,000); a row with no `id` is not added, and DEBUG logs a warning naming the view.
