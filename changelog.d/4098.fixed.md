- **A slow state save no longer costs an event its update on a view with
  `persist="server"` state (#4098).** An explicit turn waited 150 ms for its
  save and then answered a transient `state_error` ("Your last change is still
  being saved"), followed later by a full-HTML catch-up. One slow write (an
  fsync on a busy disk, a loaded process) therefore lost the event's own
  frame, and the catch-up replaced what the user had typed since; the demo's
  `@cache` browser test failed that way on CI. A turn now waits for its own
  save while holding the page's event lock, so events sent in quick
  succession all take effect in order, each gets its own frame, and storage
  ends with the last one, over WebSocket and SSE (the HTTP page-POST fallback
  already saved inside its request). The default of
  `DJUST_EXPLICIT_STATE_SAVE_TIMEOUT` is now 10 seconds, the existing stuck
  cap, after which the answer is the reload error; set it lower to keep the
  early transient answer. Covered in
  `python/djust/tests/test_rapid_events_persisted_4098.py`, with a
  test-controlled gate inside the session store holding the save.
