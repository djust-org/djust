- **The engine remembers a namedtuple shape `collections.namedtuple()` refused, and "cached per shape" is now tested (#3849).** Follow-up to #3856 from its independent review. The engine rebuilds a namedtuple's class for a native tag with `collections.namedtuple(name, fields)` (`named_tuple_class`, `crates/djust_core/src/lib.rs`) and cached only a shape it BUILT: a shape the factory refused (a `rename=True` duplicate, a leading underscore, a keyword, a non-identifier name) re-ran the factory, an `exec` that raises, on every conversion (115 ms against 92 ms per 20,000 refused rows). A refusal (`ValueError`, or the `SyntaxError` `namedtuple()` raises for fields equal only after NFKC normalisation, which was not cached either and escaped the Python shape gate, failing the render) is a fact about the shape and is cached as such; no shape raises `TypeError`, so it is no longer caught; any other failure (`MemoryError`, an exception from a patched factory) is not, and is tried again; the value still falls back to the plain tuple either way. The `lru_cache` on the Python shape gate (`_namedtuple_shape_is_buildable_cached`) had no test; both caches are now pinned by COUNTED work, the number of times the factory runs for a shape over 25 conversions (`python/tests/test_namedtuple_shape_cache_3849.py`), not a duration. Recorded, not changed, with the measurement that decided each: a namedtuple (or a plain tuple, `UUID`, `Path`) INSIDE a list or dict operand is still its JSON text (`[[1, 2]]` where Django prints `[P(x=1, y=2)]`; handing over a container that holds one keeps the whole operand in memory a second time, +24% peak RSS on a 100,000-row list, time unchanged), pinned by strict `xfail`s in `python/tests/test_namedtuple_in_container_operand_3849.py`. The custom-`__repr__` and tuple-depth items of the review stay recorded as in #3856.
