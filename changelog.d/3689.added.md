- **`params_form` declares, validates and types a view's URL parameters (#3689).** `handle_params(params, uri)` received the query string as raw strings, so the example in its own docstring (`int(params.get("page", 1))`) answered 500 on `?page=abc`, and every view that reads its URL wrote its own parsing, defaults and idea of what a bad value does. Set `params_form` to a Django form and djust binds the URL's parameters to it before `handle_params()`, which receives `cleaned_data` (the form's `initial` values fill every field the URL left out or empty, a `BooleanField` and a multi-key widget such as `SplitDateTimeField` included). Invalid input calls the new `handle_invalid_params(form, uri)` instead; its default hands `handle_params()` the initial values, and the messages reach the template as `params_errors` (`{field: [messages]}`, errors that belong to no field under `"__all__"`), so `?page=abc` renders the default page with the error. Override it to raise `Http404`, or to answer 400 through `get_http_status()`. One helper (`python/djust/_params_form.py`) runs for the HTTP GET, the stateless HTTP fallback POST, the WebSocket and SSE mount, and `url_change` (`live_patch` and back/forward); on the socket paths validation runs on a worker thread inside a guarded `handle_params` sync-turn step, so a `ModelChoiceField` can query. A view without `params_form` keeps receiving the raw dict. The guide and the `handle_params` docstring now use the form (`docs/website/guides/navigation.md`). 52 regression cases in `python/djust/tests/test_params_form_3689.py`.
