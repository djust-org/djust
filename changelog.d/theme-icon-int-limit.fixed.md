- **`{% theme_icon %}` no longer raises for a long digit string on an interpreter whose `decimal` is the pure-Python `_pydecimal` (follow-up to #3766).** `theme_icon` is documented to warn and never raise for a hostile `size`, but a `size` of 5000 digits raised `ValueError: Exceeds the limit (4300 digits) for integer string conversion` on the Python 3.15.1 CI cell (`python/tests/test_theme_icon_size_3766.py`, the `very-long` rows) while passing on 3.12. The size text matched the validation pattern (it is all digits) and `Decimal(<the digits>)` was then built outside the `try`; CPython's C `_decimal` parses digits itself, but `_pydecimal` builds the value with `int()`, which is subject to `sys.get_int_max_str_digits()`. The whole-number part of the size is now length-checked (leading zeros dropped, so `"0016"` is still `16`) before any `Decimal` is built from it, and a failure from `Decimal` anyway falls back to the default size under the existing guard. The same class in `decode_state_roundtrip` (`python/djust/serialization.py`): a user dict `{"__djust_decimal__": "<5000 digits>"}` that collides with the state tag now stays a dict, as its docstring promises, instead of raising `ValueError` on a `_pydecimal` build. The new tests (`python/tests/test_theme_icon_int_limit.py`) force the pure-Python `Decimal` and the digit limit, so they fail without the fix on every interpreter.
