- **A SECRET floor field of a form is never rendered with its stored value, and the column is protected from being rewritten by the empty control (#3797). BREAKING for a template that relied on a secret floor field echoing its value.** #3796/#3798 refused every way a template could READ a model form's floor-field value back, but `{{ form.password }}`, `{{ form.as_p }}`, `{{ form }}` and `{% for x in form %}{{ x }}{% endfor %}` still printed `value="..."` for a floor field with a plain widget (the `password` column over a `TextInput`, a declared `api_token`), the body of a `Textarea`, the `selected` option of a `Select`, the `checked` of a checkbox and the parts of a `MultiWidget`; `{{ formset.as_p }}`, `as_widget`, `as_field_group`, `BoundField.render()`, the `{name: html}` snapshot of a form kept in LiveView state and the `BoundField` handed to a bridged `{% load %}` tag or filter (`{% render_field form.password %}`, `|add_class`) did the same. Such a field's control is now drawn the way Django draws a field that has no value, by Django's own widget on a copy of the `BoundField` (`value()` and `initial` answer `None`; its own posted keys, including Django 5's hidden-initial value, are removed from a copy of the form; its validation messages that interpolate the value, such as a `disabled` `ChoiceField`'s `invalid_choice`, are replaced by a generic one): no `value=`, an empty `<textarea>`, no `selected`, an unchecked box, empty `MultiWidget` parts, with no cooperation from a custom widget. **Only SECRET-LIKE floor fields are blanked**: a password widget, a name with a `password` / `secret` / `token` / `key` / `hash` / `salt` / `pwd` / `otp` word (`api_token`, `secret_key`), or a `sensitive_field_types` column. Privilege flags (`is_staff`, `is_superuser`), selects and ordinary declared-sensitive text (`email`, `first_name`) keep drawing their real state, because an empty control is posted back empty (a blank text control clears the column, an unselected `<select>` posts its first option, an unchecked box posts nothing and a classic POST of the stock `UserChangeForm` would demote a superuser). **The column is protected where Django can protect it, on the FORM FIELD**: `FormMixin.get_form()` (so `ModelFormMixin`) marks every blanked field `disabled=True` on a form that edits an existing row, so Django ignores the posted value and keeps the stored one; HTML `disabled` / `readonly` and leaving the control out still save `""`. A plain `ModelForm` in a classic view cannot be protected at render time: the new system check `djust.S014` reports an editable secret floor field in a `ModelForm` with the fix. djust's component tags draw an editable secret floor field empty too; another editable floor field keeps its value (as before). Kept by their own contract: Django's `ReadOnlyPasswordHashWidget` (exact type; a masked summary) and `PasswordInput(render_value=True)` (the author's explicit echo); the model's `djust_serialize_sensitive_fields` takes a field off the floor entirely. A value the project's own code puts elsewhere (`widget.attrs`, `help_text`, a closure holding the form) and a bridged tag that walks the real FORM it is handed are not covered.
