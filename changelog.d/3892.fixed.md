- **`{% for u in users|dictsort:'username' %}{{ u.pk }}{% endfor %}` over a QuerySet, or a QuerySet / `list[Model]` on a LiveView, no longer renders an empty loop when the template reads `username` nowhere else (#3892).** A path-JIT row holds only the fields the template reads, and the template-variable extractor (`extract_template_variables`, `crates/djust_templates/src/parser.rs`) attributed `u.<field>` reads in a loop body and nothing else, so a field named only in a filter ARGUMENT was never in the row; Django's `dictsort` answers `''` for a missing key rather than raising, so the loop was silently empty. The quoted argument of `dictsort` / `dictsortreversed` (a table of the built-in filters that read a named attribute of each item, measured against Django: exactly these two) and the `by` attribute of `{% regroup %}` (which grouped by `None` on a LiveView) are now filed on the list beside the fields the body reads, through a loop, a `{% with %}` alias, a `{{ }}` or an `{% if %}` operand, and a nested path (`page.users`). One extractor serves `DjustTemplateBackend` and the LiveView, so both are fixed together. The key is filed only when the items are also read by field: with nothing else singled out the row is serialized whole, which already carries the key and the `__str__` a bare `{{ u }}` prints, so `{% for u in users|dictsort:'name' %}{{ u }}` keeps working. A key that is not a plain path (empty segment, a segment starting with `_`, as Django refuses) is ignored, and the serialization floor applies to a sort key as it does to `{{ u.password }}`. Not fixed here and filed: a context-variable key (`dictsort:key`, #3910), a dotted key the Rust `dictsort` cannot sort by (#3912), and a loop variable read whole next to a field (#3911). New cases in `python/tests/test_item_key_filters_3892.py`; the strict xfails of `TestDictsortOverJitRows` in `python/tests/test_sliced_list_of_models_3888.py` are removed.
