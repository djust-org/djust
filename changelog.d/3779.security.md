- **`LIVEVIEW_CONFIG['theme']['css_prefix']` is validated when the config is read; a prefix that holds markup can no longer break out of the theme `<style>` blocks (#3779).**

  `get_css_prefix()` returned the raw config string. It reached `generate_component_css`, `generate_css_for_state` and the critical-CSS split, which print it into `.{prefix}btn { ... }` inside `<style>` blocks that `python/djust/theming/templates/djust_theming/theme_head.html` renders under `{% autoescape off %}`. `LIVEVIEW_CONFIG = {"theme": {"css_prefix": "x</style><img src=x onerror=alert(1)>"}}` printed a parsed `<img onerror>` element in `{% theme_head %}`, `{% theme_css %}` and `{{ theme_head }}` (the context-processor chunk). This is settings-level, not request-reachable: it needs a hostile or careless value in settings, which is why nothing had shown it. `cookie_namespace` was regex-validated and `direction` allow-listed; `css_prefix` was neither.

  `get_theme_config()` now raises `ImproperlyConfigured` for a `css_prefix` that is not a string of ASCII letters, digits, underscores and hyphens (`[A-Za-z0-9_-]*`), the way it already does for `cookie_namespace`. `""` (the default) and `None` still load. Every reader goes through that function (`theme_head`, `theme_css`, the context processor, the CSS views, `ThemeMixin`, `theme_form` / `theme_form_errors`, the component and page tags, `get_css_prefix`), so one check covers them all, in both the Django and the Rust template engines. It is an exception at load rather than only a system check because `manage.py check` does not run under `gunicorn` or `uvicorn`: a check-only gate would leave the injection live in production. The three generators that also take a prefix as an ARGUMENT, bypassing the config (`generate_component_css`, `CompleteThemeCSSGenerator`, `DesignSystemCSSGenerator`), run the same validator, so `generate_css_for_state(state, css_prefix=...)`, `generate_critical_css_for_state`, `generate_deferred_css_for_state` and `generate_theme_css` are covered through them.

  What changes: a project with a prefix outside that alphabet now fails at the first theme render with a message that names the setting (previously it rendered a broken or hostile stylesheet). No documented or tested prefix is affected: `dj-`, `dj`, `djt-`, `myapp-` and `""` render byte for byte what they did (43 renderings across prefix, tag and engine, captured before the change, are pinned in `python/tests/test_theme_css_prefix_validation_3779.py`).

  Related, same file: `check_css_prefix` (`djust_theming.E004` / `W002`) used `re.match(r"^...$")`, and `$` also matches before a trailing newline, so a prefix of `"dj-\n"` passed the check; it now uses `fullmatch`. The check reads the unvalidated config so it can still REPORT a prefix the loader refuses (E004) instead of dying in `get_theme_config()`. E004 stays stricter than the loader (it also wants a leading letter): the loader draws the line at "cannot carry markup", the check at "is a valid class prefix".
