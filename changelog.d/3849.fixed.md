- **A native component tag gets a namedtuple as the namedtuple it is, and recovering a large tuple costs less counted work (#3849).** Follow-ups to #3843 (#3768). (1) `{% approval_gate reject_label=v %}` over `P(1, 2)` printed `(1, 2)` on the Django-backend engine (`[1, 2]` before #3843; Django prints `P(x=1, y=2)`), and seven cells flipped from their default to `(1, 2)`: `dashboard_grid` `gap` / `row_height`, `map_picker` `height`, `resizable_panel` `initial_size` / `min_size` / `max_size`, `sortable_grid` `gap`. Two causes, one per layer: `serialize_value(for_render=True)` rebuilt every tuple as `tuple(items)` (a namedtuple is now rebuilt positionally and keeps its type, so `{{ v }}`, `{{ v.x }}` and the filters match Django too; a subclass whose `__new__` cannot be rebuilt degrades to the plain tuple), and the engine's narrow ask (`TYPED_ARGS_STANDINS_ONLY`) handed over a `Value::Tuple` but not a `Value::NamedTuple` (it does now). `_parse_args` returns a `NamedTupleValue`, a `TupleValue` that is a `list` (the `isinstance(x, list)` slots keep working) and prints `P(x=1, y=2)`; a namedtuple nested in a tuple is converted too. Pinned for every shape on both native entry points (the Django-backend engine and `RustLiveView`) against Django's own tag: plain, namedtuple (one field, none), tuple in namedtuple and the reverse, nested, empty, one-element and a tuple subclass (`python/tests/test_typed_tuple_shapes_3849.py`). Recorded, not changed: a tuple subclass that overrides `__repr__` and a namedtuple with a custom `__repr__` print the default (the engine keeps no class), and a tuple held as LiveView state is a list before the engine (`normalize_django_value`, unchanged). (2) The review measured a 2,000,000-element tuple at +34% time and +39% RSS, more than #3843 stated. The avoidable part is gone and pinned by COUNTED work, not a duration: `_parse_args` no longer decodes the JSON text of an operand the typed value replaces (the test asserts `json.loads` never sees it), and `_from_typed` copies a tuple with no tuple member in one C-level pass instead of a Python loop per element (the test asserts the executed source lines are the same for 10 and 20,000 elements). Release build, one process per case, a loaded machine: 1.19 to 1.29 s and 1,054 MB before, 1.07 to 1.16 s and 1,022 MB after. What remains is the engine's own: the operand is serialised once as the string argument, resolved a second time as a typed value and built once as Python objects. A lazy sequence view was considered and not done: ~55 handlers read a list slot with `isinstance(x, list)`. Not addressed: the tuple-depth label difference at 1,100 and 3,000 levels (the render raises `RecursionError` in `serialize_value` first, unchanged) and the run-to-run variation of the reproducible cell counts (the reviewer's own measurement note). Gate-off verified: 9 Python mutations and 1 Rust mutation, all caught.
