- **`DJUST_STATE_SAVE_INTERVAL`: a WebSocket or SSE turn may answer before its state is saved (off by default).** Set to a number of seconds (0.5 to 60), a socket turn of a view with no declared `persist=` field sends its reply without waiting for storage, and the view's state is saved no later than the interval after the first unsaved change, when the connection closes, before a navigation replaces the view, and at the ASGI `lifespan` shutdown. A URL change, a turn that queues navigation, a turn whose handler wrote `request.session`, `@event_handler(save=True)`, `self.save_state()`, a strict store and a view with declared persistence still save before the reply; the HTTP fallback is unchanged. A view's `state_save_interval` overrides the setting; system checks `djust.C040` (an interval that cannot be used) and `djust.C041` (an interval a strict store makes moot). With an interval set, each socket mount and fallback request for a tab writes a new holder record in the session, and a socket writes the tab's state only while the record is its own, so an older connection for the same tab cannot write over a newer one, even after the tab's saved state was evicted, deleted or expired (exact under a database row lock; on cache, file and SQLite a writer paused between its read and write is not refused). The default (`0`) keeps every turn saved before its reply. See `docs/website/state/save-frequency.md`.
