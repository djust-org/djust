- **`http_status_of_state` decides a page's HTTP status once, from the state it already has (#3688).** `LiveView.get_http_status()` (#3558) answered 200 unless a view overrode it, so a page that draws its own not-found state answered 200 unless that view, and every other view like it, remembered the override. Set `http_status_of_state = {"not_found": 404, "forbidden": 403, "gone": 410}` once, on a base view, and the default `get_http_status()` answers the status mapped to the view's `state` (`state_attribute` names another attribute). Only a string state is looked up; the map defaults to empty, so a view that declares nothing, and a view that overrides `get_http_status()`, answer exactly as before. Only the HTTP response has a status (a socket frame has none), and the streaming render answers it too. 13 regression cases in `python/djust/tests/test_http_status_of_state_3688.py`. Behavior note: `http_status_of_state`, `state_attribute` and `params_form` are now framework class attributes, so a view with `exposure_policy = "explicit"` cannot declare a `state()` field under those names.
