- **The HTTP fallback routes an embedded child's events to the child (#3104).** Over HTTP-only a `{% live_render %}` child's event reached the parent (since #3159, it was refused instead). The request now renders the page once to register its children, then validates, authorizes (the page's view and object permission, the child's own, `@permission_required` on the handler) and runs the handler on the child, and answers with the child's own HTML in an `embedded_update`, as WebSocket and SSE do; a sticky child that opted in to state persistence keeps its state across events. This needs a child's id to repeat between the page GET and the POST that follows, so over HTTP an auto-assigned id is named for what the child is (`child_<hash>` of its view path and tag arguments, with a numeric suffix for a repeat) instead of coming from a process-wide counter: a page that changes between the GET and the POST (a list that gained a row in another tab) never makes an id name a different child, and an id whose child is gone is refused. An id that names no child, an explicit-exposure child, or a child of an explicit-exposure page is still refused with "Embedded view not found" (an explicit child's turn is authorized against a mount binding a stateless request does not have). A non-sticky child's state is not persisted over HTTP: each request re-creates it, as every parent render always did.
