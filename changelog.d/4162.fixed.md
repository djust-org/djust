- A handler that wrote only `request.session` (no view-state change) had its write dropped: over the WebSocket nothing was stored, and an in-place change (`request.session["cart"].append(x)`) was lost on every transport, because Django's `SessionMiddleware` saves only a session marked `modified`. In an explicit view the write, including an in-place change to a value the handler read, is now stored before the turn's reply over the WebSocket, SSE and the HTTP fallback, merged into the session as storage holds it, with or without `DJUST_STATE_SAVE_INTERVAL`; the same for a component's handler, a sticky child's handler, and `start_async()` work, whose write is stored with its result under the result's own authorization. An HTTP fallback request of a legacy view stores an in-place change too. A turn that does not write the session adds no session write (#4162).
