- **`connected()` and `disconnected()` are real LiveView hooks (#3007).** `connected()` runs once per live (WebSocket or SSE) mount, after `mount()` (or a state restore) and `handle_params()` and before the first render, so state it sets is in the first frame; raising fails the mount like `mount()` does. `disconnected()` runs once for each view that reached `connected()`, when its live mount ends: the socket or stream closes, or a `live_redirect`, a second `mount` frame, an `unmount` frame or a revoked authorization releases the view. Both are regular (not `async def`) methods and run on a worker thread (the ORM works), `disconnected()` under the tenant the view mounted with, and an exception in `disconnected()` is logged without stopping the teardown. The HTTP render and the HTTP POST fallback never call them, `disconnected()` is not called if the process dies, and views a template embeds with `{% live_render %}` do not get them. A view that already defines a callable `connected` or `disconnected` now has it called; a state attribute of that name is ignored. Both are listed in `djust.schema.LIFECYCLE_METHODS` again, and the LiveView API reference states the lifecycle contract, including what is not guaranteed. 22 regression cases in `python/djust/tests/test_lifecycle_contract_3007.py`.
