- **A lazily-rendered slot is now filled over the page-POST fallback, instead of being left empty (#3252).** `{% live_render ... lazy=True %}` renders a `<dj-lazy-slot>` placeholder and stashes a thunk whose fill envelope is transport-agnostic — an inert `<template id="djl-fill-X">` plus an activator, which `50-lazy-fill.js` applies (its `DOMContentLoaded` auto-scan already covers the activator running before the bundle defines `lazyFill`). The WebSocket consumer and the SSE chunk emitter both ran those thunks; the plain page render did not, so a browser with neither transport got an empty slot even though the server could render it. The page render now runs them and appends the envelopes. Nothing else changes: the placeholder is still emitted and the client still performs the replacement, the `visible` trigger still defers until the slot is on screen, and the stashed thunks are cleared either way so a re-used view instance cannot leak them into the next response. The `dj-lazy` *attribute* form (`<div dj-view=… dj-lazy>`) is a different mechanism with no server-side registration and is unchanged — it is still refused over that transport. It uses one authoritative pass — the page render, not the VDOM-diff baseline that renders the template a second time — so a slot under an explicit-exposure page, whose child ids differ between the two passes, still fills exactly once. 4 regression cases in `python/tests/test_lazy_slot_http_fallback_3252.py`.
