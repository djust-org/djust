- **`LIVEVIEW_CONFIG["http_fallback_background_timeout"]` bounds the work the HTTP page-POST fallback runs inside the request** (#3634). Since #3630 the fallback runs `start_async` / `@background` work before it answers, and nothing bounded a task: a `mount()` that starts a watcher held every POST open for as long as it ran. Set the key to a number of seconds (default `None`, no deadline, and no change in behaviour) and one POST waits for background work for that long in total, across mount's work, the handler's and a page's after a child event. Each task then runs on a worker thread (a sync callback runs on the request thread otherwise, so no timeout could free the request). At the deadline the fallback answers from the state it has: the running task is abandoned, every task still queued is dropped without starting, a warning names them, and `handle_async_result` receives a `TimeoutError` as `error=` for each. An `async def` callback is cancelled; a sync callback cannot be and keeps running, its result discarded (it can still write to the view the answer was rendered from). At most 16 background worker threads (abandoned ones still alive plus ones a POST is waiting for; slots are reserved atomically, so concurrent POSTs cannot overshoot) may exist per process; past that a task is not started (warning, `TimeoutError` for `handle_async_result`). An `async def` callback runs on a private event loop under the key. A value that is not a number from above 0 up to `threading.TIMEOUT_MAX` means no deadline, and system check `djust.C028` reports it. The guide's hard-limit paragraph is replaced with this contract (`docs/website/guides/http-only-mode.md`).
