- **A model form's values are held to the serialization floor under the native engine (#3790).** `ModelForm.initial` is `model_to_dict(instance)`, a plain `dict` of strings by the time a template reads it, so the engine's walk never met a `Model` and the model proxy had nothing to refuse. On a `UserChangeForm` bound to a `User`, `{{ form.initial.password }}`, `{{ form.password.value }}` and `{{ form.password.initial }}` printed the password hash while `{{ form.instance.password }}` was empty: the same secret by a different spelling. So did `form.cleaned_data.password` (a disabled field validates to its `initial`), `form.data.password`, `form.password.data`, `form.password.subwidgets.0.data.value` (and `form.password.0`), the `as_text` / `as_textarea` / `as_hidden` renderers (they swap in a widget that prints the value), `{% for f in form %}{{ f.value }}`, `form.visible_fields`, `form.get_context.fields…`, `form.password.form.initial.password`, a `{% with %}` alias of any of these, and the same paths as the operand of a `{% load %}`-bridged tag. The floor is the model's, not the word `password`: `is_superuser`, `is_staff`, `DJUST_SENSITIVE_FIELDS`, a per-model `djust_exclude_fields` and `djust_serializable_fields`, the `djust_serialize_sensitive_fields` opt-out, and the field TYPE floor (`sensitive_field_types`, #1987) are all consulted through the one authority the model proxy uses (`_attr_is_serializable`).

  The cure is at the chokepoint where the engine reads a path, not at three spellings. After the root and after every segment of a path, the engine now calls `djust.serialization._protect_sidecar_walk`, which is `_protect_sidecar_value` plus two arms: a `ModelForm` becomes a floor proxy whose `initial` / `data` / `cleaned_data` are COPIES without the model's floor fields (the form itself is never mutated: `initial` is what a disabled field validates against, and a rendered form still saves without clearing the user's password), and the `BoundField` of a floor field becomes a proxy that refuses `value`, `initial`, `data`, `subwidgets` (and indexing or iterating the field) and the three renderers that swap in a value-printing widget. A refused name is a missing name: it renders empty, as `form.instance.password` does. Every other `BoundField`, and every field of a form that holds no floor field, is the real object, byte-identical to before (checked against Django's output for the benign paths). `template_bridge_floor` walks a bridged tag's operand paths through the same function.

  **Policy, stated plainly.** Django itself prints all of these. The floor is the stricter policy djust adds (SECURE_DEFAULTS Pattern 1), and the Django template engine is unchanged by this fix; only the native engine and the bridge's operand walk apply it. A template that reads a floor field's value back through a form (for example a hand-written `<input type="checkbox" {% if form.is_staff.value %}checked{% endif %}>`) now renders it as missing, exactly as `{% if user.is_staff %}` already did. The widget the form's author chose still renders, because that is the form rendering itself and the view author decided it: `{{ form.password }}`, `{{ form.as_p }}` and `{{ form }}` are unchanged (Django's `ReadOnlyPasswordHashWidget` shows a summary of the hash, not the hash).

  **What a tag is handed.** A bridged tag is the application's own Python (djust's component readers call `bound_field.value()`; a third-party form tag renders the widget), so it is handed the real form and the real `BoundField`, never the proxy: a proxy would draw a `User`'s `is_staff` checkbox unchecked and the next save would clear it. Only a template PATH is floored, so `{% tag x=form.initial.password %}` receives nothing and `{% tag form.password %}` receives the field. This is why the engine has two entry points now: `_protect_sidecar_walk` for a path the template spells (`Context::walk_live`, the sidecar walk, the bridge's operand walk) and `_protect_sidecar_value` for an object handed to a tag (`value_into_handler_pyobject`, the handler dict). The Rust side looks the walk function up by name and falls back to the leaf floor when it is absent, so it is never weaker than before.

  **Reach, measured.** A LiveView's own top-level `self.form` attribute was never reachable by these paths (`mixins/rust_bridge.py` leaves a `BaseForm` out of the raw-object sidecar), so there it was not a leak. The exposed shapes were a standalone render (`DjustTemplateBackend`, `render_template`) with a form in the context, and a form held by another object in a LiveView (`page.form.initial.password`).

  **What this does not floor.** A plain `Form` (no model behind it, so no model floor: `PlainForm(initial=model_to_dict(user))` is the view author handing the template a dict, like any other dict); `form.fields.<name>.initial` (a declared or model-default value, never the instance's); a tag author's own Python and a `takes_context` tag reading the context itself; the form's own widget rendering (`as_p`, `{{ form.field }}`), which is the author's choice; and the Django template engine.

  Regression cases in `python/tests/test_form_initial_floor_3790.py` (the table of spellings, run for an unbound and a bound `UserChangeForm`, each with a Django-engine control that prints the hash so the comparison is never two empty strings; the model's floor sources; benign-output parity with Django; the form left whole and still saving; the real object handed to a tag; `LiveViewTestClient`, HTTP GET and WebSocket mount). Each mechanism is gate-off tested separately. The code is `_protect_sidecar_walk`, `_SidecarFormProxy` and `_SidecarBoundFieldProxy` in `python/djust/serialization.py`, `protect_sidecar_walk_strict` in `crates/djust_core/src/context.rs`, and `release` in `python/djust/template_bridge_floor.py`. Requires the matching compiled extension (rebuild with `make dev-build`).
