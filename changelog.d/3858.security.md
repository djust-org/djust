- **A wizard's data limits are a total across its steps, `remove_row` asks the form-data bound before it stores a client-named key, and the three limits are validated when written in code (#3858).** The review of #3857 found that `WizardMixin` bounded each step's data alone, so a four-step wizard of `required=False` fields kept about four times `max_form_members` (360,000 members against 100,000) and handed every one of them to the template engine on every event; `max_form_data_size` and `max_form_members` now bound every step together (`max_form_fields` stays per step, a step being a form). `FormSetHelpersMixin.remove_row` and `remove_row()` stored `<prefix>-DELETE` for a client-named prefix with no check (3,000 calls reached 3,000 keys against `max_form_fields` = 1000); past a limit the call is now a logged no-op, and the formset's own management and row keys do not count as the client's. `config.set()` / `config.update()` of `max_form_fields`, `max_form_data_size` or `max_form_members` skipped the validation done at load, so `'abc'` made every form event raise `TypeError`, `-5` refused everything and `3.7` / `True` were accepted: a value that is not a non-negative integer is now the default, as at load. The refusal messages and the production "no limit" warning name the setting (and which one is 0). **Behaviour change:** a wizard whose steps together hold more than the limit is refused (raise `max_form_members` / `max_form_data_size` for a long wizard).
