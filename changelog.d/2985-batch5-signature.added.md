- **SignaturePad now ships its interaction, and a safe decoder for what it sends (#2985, batch 5).** The component rendered a `dj-hook` that no shipped script answered. `components/static/djust_components/signature-pad.js` draws on the native canvas with pointer events (mouse, touch and pen with pressure; the page does not scroll while drawing), keeps the strokes as points so Clear, Undo (last stroke) and a resize or pixel-ratio change redraw faithfully, renders sharply on high-DPI screens, follows its container's width, and exports the PNG at the pad's own size (at most twice, never the screen's). Save with nothing drawn sends nothing and says so; otherwise `{signature: "data:image/png;base64,..."}` goes to `save_event` (and the hidden form field), never longer than the new `max_bytes` (default 200 KB): the signature is re-rendered at a lower resolution until it fits and refused when it cannot, and when the server answers "Message too large" (the default WebSocket limit is 64 KiB) it is sent once more at a size that fits. "Type instead" is the keyboard alternative: a text field whose name is drawn in a script font (`typed=False` turns it off). New `djust.components.signature.decode_signature_data_url` validates the value without decoding pixels (exact prefix, strict base64, size caps checked before decoding, PNG magic bytes, every chunk and CRC, dimensions and pixel count within limits, an image stream that inflates to exactly what its header promises) and returns the original bytes with their size; the handler must use it because the value is the browser's claim. Markup changes are additive only (`data-max-bytes`, `role`/`aria-label` on the canvas, the typed field, Undo and mode buttons, a status region), on the component class, template tag and Rust handler alike; a byte comparison of 7,542 renders against the previous release is identical once those are removed. The script registers in `window.DjustHooks` and only when neither hook registry already holds that name. 2 components from the issue remain.
