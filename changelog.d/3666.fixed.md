- **A tag that takes an object renders under the Rust engine as it does under Django (#3666).** `{% field_error field=form.name %}` rendered nothing under the Rust engine and the error under Django: the engine hands a native handler its operands as strings and JSON, so a `BoundField` arrived as its widget HTML, a `Form` as its `str`, a `datetime` as `str(datetime)` and an item of a list as whatever `str` gives. The tags that take an object are measured, not listed by hand (`scripts/lib/template_library_parity/objects.py` renders every parameter of every tag with a value that records how it is used): `field_error`, `form_errors`, `combobox`, `rich_select`, `relative_time`, `avatar_group`, `conversation_thread`, `notification_popover` and `toast_container`. They no longer have a native handler class (`rust_handlers.OBJECT_ARGUMENT_TAGS`): each is registered as the `{% load %}` bridge handler, so the Python tag's own node renders it and the output is Django's by construction. They are registered up front, so they still work in a template that does not load the library. **Behaviour change:** the markup of `toast_container`, `notification_popover`, `combobox`, `relative_time` and `rich_select` under the Rust engine is now the Django tag's (`toast_container` is `dj-toast-container`, not `toast-container`), and a `{% toast_container %}` with no `toasts` is a `TemplateSyntaxError` as it is under Django (the handler used to read a context variable named `toasts`). Not changed: a value bound by `{% for %}` or `{% with %}` inside the template still reaches a tag as its `str`, and a callable operand is not called, for every tag. New `python/tests/test_native_handler_fidelity_3666_3667.py`; the parity baseline rows for the nine tags improve.
