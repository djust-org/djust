- **A native component tag gets a tuple, a UUID and a Path as the value it is, not the engine's stand-in (#3768).** The Rust engine hands a native handler its operands as text or JSON, so `{% approval_gate reject_label=v %}` over `v = (1, 2)` printed `[1, 2]` where Django's tag prints `(1, 2)`, and `{% live_counter value=v %}` over a `UUID` showed `0` where Django counts `int(uuid)`. `scripts/lib/template_library_parity/typed_values.py` measured 495 such cells (cells where the Python tag renders a value differently from its stand-in, and the engines agree on the stand-in) over 208 tags, 15 value types and 21,390 cells; **the count is now 45**, 450 fewer. Over ALL 21,390 cells (Rust output equal to Django's, exact status and text, base against this change) 517 more now agree, 0 newly disagree, 15,341 agreed before and still do, and 5,532 still differ for reasons unrelated to a stand-in. Every inline and block component handler now declares `TYPED_ARGS` (one wrapper at registration, not a class attribute on ~180 of them) and `_parse_args`, the one place they read their operands, takes back a `UUID`, a `Path` and a `tuple`. A tuple comes back as `TupleValue`, a `list` subclass that prints like the tuple: ~55 handlers read a list slot with `isinstance(x, list)`, and a real `tuple` turned `rows=my_tuple_of_dicts` into an empty table (the first version of this fix did that to `dependent_select`; a measurement over 13 probe shapes found it). Both the conversion and the printing walk an explicit stack: a tuple nested 500 deep rendered before this change, and a recursive walk raised `RecursionError` for it. (Past ~1000 levels the engine's own context serializer raises on the unchanged code, before any handler runs.) The block tag needed the engine's twin of the inline channel (`add_typed_operands`, the one function both call sites use). A wrapped handler also declares `TYPED_ARGS_STANDINS_ONLY`, so the engine hands over only a tuple or an object operand and a large list or dict is not materialised a second time as Python objects. **Behaviour change:** a `UUID` or `Path` given to a parameter that takes a list or text used to render (the handler iterated the value's text as characters) and now raises `TypeError`, as Django's tag does, for `animated_number separator=`, `carousel images=`, `data_grid columns=` / `rows=`, `multi_select options=` / `selected=`, `notification_center notifications=`, `table_of_contents items=`, `tag_input suggestions=` / `tags=` and `tree_view nodes=` (11 parameters of 8 tags, each for both types; `test_both_engines_raise_the_same_error`). **Cost,** release build, base against this change, one process per case, a loaded machine: a 100,000-row `data_table` 2,301 / 2,273 ms to 2,311 / 2,319 ms (+0.4% / +2.0%), peak RSS 746 / 747 MB to 772 / 772 MB (+3.5%); a 1,000-point `bar_chart` +0.8% / +1.5%, RSS unchanged; a scalar tag about +3 to +5 µs per call (`badge` 33 / 34 µs to 36 µs, `modal` 38 µs to 41 / 43 µs). A 2,000,000-element tuple operand, the case the recovery exists for, is materialised as Python objects again: 5,027 / 5,022 ms to 5,409 / 5,416 ms (+7.6% / +7.8%), peak RSS 1,122 / 1,235 MB to 2,220 / 1,670 MB (the two rounds disagree; linear in the tuple).
