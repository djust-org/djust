- **Re-reading held rows after a write changes what some views do (#4112).** Each change, with its escape:

  A handler that writes to a table the view reads (through a held QuerySet, a cached property or a query its render runs) and changes nothing else on the view now renders; it used to answer `noop` with the old rows. Escape: `self.skip_render()` in that handler; the rows are then re-read at the view's next render. A write to a table the view does not read is still a `noop` with no re-read: on a view holding 5,000 rows, a click that inserts into an unrelated table measured a `noop`, 3 statements and 2.8 ms, against a `noop`, 3 statements and 2.5 to 2.6 ms on `main`.

  When a re-read happens it is everything the view holds, not only what the write touched: every held QuerySet (one query per prefetch level) and every cached property, then the render of the rows (measured 220 to 228 ms for 5,000 held rows on SQLite). Escape: `frozen_rows` for a deliberate snapshot or an expensive cached value.

  A write djust cannot name (raw SQL with unquoted table names, a schema-qualified name, `TRUNCATE`, `MERGE`, a `WITH`, DDL, several statements in one), a read it cannot follow (a function or `ONLY` in `FROM`), a cached value or held rows not filled by a recorded render, and a restored state each make the next write re-read everything: slower, never stale for the writes djust sees.

  A `handle_tick()` that writes to a table the view reads now renders on every tick. Escape: list a heartbeat table in `DJUST_IGNORED_WRITE_TABLES` (writes to `django_session` and to `DatabaseCache` tables never count), or call `self.skip_render()` in the tick. djust's own per-turn session and user checks are not reads of the view, so a tick that writes `auth_user` does not render for that reason.

  Writes the database makes by itself (triggers, `ON DELETE CASCADE`, rules, a model over a database view) are not seen. `DJUST_REFRESH_ON_ANY_WRITE = True` (off by default) makes every write a view's step makes re-read everything; the new Info check `djust.C042` names unmanaged models and `DB_*` cascades while it is off.

  A project test that counts queries on a turn that writes a table the view reads sees one more per held QuerySet (one per prefetch level).

  A render step now records the view's reads: `sync_step(view, "render", fn)` returns a wrapper of `fn` rather than `fn` itself.

  `connection.execute_wrappers` is no longer empty: djust puts one recorder at index 0 of every connection's list when it connects. Measured on SQLite in process: about 0.14 µs per query outside a view's step or render, 0.5 to 0.7 µs inside one. A project's `execute_wrapper()` blocks still add and remove their own.
