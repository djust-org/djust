- **Re-reading held rows after a write changes what some views do (#4112).** Each change, with its escape:

  A handler that writes to a table the view shows (one a held QuerySet reads, or one its own queries read) and changes nothing else on the view now renders; it used to answer `noop` with the old rows. Escape: `self.skip_render()` in that handler; the rows are then re-read at the view's next render. A write to any other table is still a `noop` with no re-read: on a view holding 5,000 rows, a click that inserts into an unrelated table measured a `noop` with 3 statements and 2.8 to 3.3 ms, against a `noop`, 3 statements and 2.7 to 4.2 ms on `main`.

  A write to a table a held QuerySet reads re-reads all of it, however many of its rows changed: one query per prefetch level, and the render of the rows (measured about 197 ms for 5,000 held rows on SQLite). Escape: name the QuerySet in `frozen_rows` if it is a deliberate snapshot.

  A `handle_tick()` that writes to a table the view shows now renders on every tick. Escape: list a heartbeat table in `DJUST_IGNORED_WRITE_TABLES` (writes to `django_session` and to `DatabaseCache` tables never count), or call `self.skip_render()` in the tick.

  Every `cached_property` of the view is computed again after a write to a table the view's own queries read, as it would be on a new request. Escape: name it in `frozen_rows`, which covers cached properties as well as QuerySets.

  When the table of a write or of one of the view's reads cannot be determined (a `WITH` that writes, `CREATE`, a function in `FROM` such as `json_each()`), every held QuerySet and cached property is read again: slower, never stale.

  A project test that counts queries on a turn that writes a table a held QuerySet reads sees one more per such QuerySet (one per prefetch level).

  `connection.execute_wrappers` is no longer empty: djust puts one recorder at index 0 of every connection's list when it connects. Measured on SQLite in process: about 0.15 µs per query outside a djust turn, 0.35 to 0.4 µs inside one. A project's `execute_wrapper()` blocks still add and remove their own.
