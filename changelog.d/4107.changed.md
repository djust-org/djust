- **A view's state is saved server-side automatically; client exposure stays explicit.** What a page view sets on `self` now survives the next request, a reconnect and a move to another process, on every transport including the stateless HTTP fallback: public attributes and `state()` fields whose values are plain data (`None`, booleans, numbers, strings, lists, dicts) are saved in the server-side session after each event that changed them and put back after `mount()`, before `handle_restore()`. No declaration is needed, and nothing becomes renderable or client-settable by being saved: the template, the client state, signed snapshot tokens and debug payloads still come from `state()` declarations and `get_context_data()` only. Not saved: names with a leading underscore, a field declared with the new `state(..., persist=False)`, djust's own attributes, attribute names on the serialization floor (`password`, `is_staff`, `is_superuser`, `DJUST_SENSITIVE_FIELDS`), sensitive `FormMixin` fields, and any value that is not plain data (model instances, querysets, `Decimal`, dates, the request, the user); such a value is skipped without failing the event and named once on the `djust.automatic_state` logger. Saved state over 64 KB, 10,000 values or 16 levels leaves its largest attributes out, with a warning. State written by different code of the view class (after a deploy that changed it, or a bumped `exposure_schema_version`) is dropped and the view mounts fresh; a full page load also starts fresh. The session is not written when the state did not change. `persist="server"` keeps its strict behaviour (an unsaveable or oversized value is an error). `exposure_policy = "legacy"` views get their state back over the HTTP fallback through the same store. `djust.V029` now reports only what is still lost: a handler that changes a `_private` attribute, or a `persist=False` field, that a later event reads.
