- **V023 checks `params_form`; `LiveViewTestClient` drives `handle_params`; `params_form`, `http_status_of_state` and `state_attribute` are reserved names (#3706).** A `params_form` that is not a form class raised `ImproperlyConfigured`, and a form whose `__init__` needs an argument beyond `data=` (a user, a queryset, a tenant) raised `TypeError`, both on the first request. `manage.py check` now reports each as **V023** (Error), using the request path's own verdicts (`djust._params_form.form_class_problem` and `construction_problem`) so the check cannot call usable a form the request path refuses. `LiveViewTestClient.mount()` followed `mount()` with nothing, so a view declaring `params_form` could not be unit-tested through it: it now calls `handle_params(params, uri)` right after `mount()`, as the HTTP GET and the socket mount do, through the same `params_form` decision, and takes `mount(query_params={...})` (a mapping or the query string) for the URL's parameters and a new `url_change(query_params)` for a `live_patch` / back-forward frame. The three names are also in the framework-internal attribute set: a legacy view that assigned `self.state_attribute = ...` (or `params_form`, `http_status_of_state`) in `mount()` published it as reactive state; an `exposure_policy = "explicit"` view could already not declare a `state()` field under them, and a test now pins that. Not in this change: a `LIVEVIEW_CONFIG["http_status_of_state"]` project-wide default (it needs a precedence rule between the view attribute and the config), a V013-style check that depends on it, the `Http404`-from-`mount()` alternative, and a per-field `handle_invalid_params` fallback; #3706 stays open for them. Documented in the navigation guide, the testing API reference, `docs/system-checks.md` and the error-code reference.
