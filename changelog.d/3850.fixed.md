- **The safe-markup guard no longer trusts a class attribute the class body may not define, and checks where `safe_url` output lands in the string-building forms it knows (#3850).** Soundness follow-ups from two reviews of #3848. In the 322-function review corpus, the fuzz programs run (4,800 here, 12,800 in the review) and the real tree the guard clears nothing new (the audit baseline is unchanged except the corrected `JSChain.__html__` reason); that is measured, not proved. A class attribute defined only inside an `if`/`try`/loop, or deleted by `del C.X` / `del X`, is trusted only when the class has no `__getattr__` (on it, on a subclass in the file, or assigned from outside), no base other than `object` and no class keyword; the same holds for a method. The position check on `safe_url` / `url_attr` / `safe_css_*` (text or a quoted value, never an unquoted attribute or a tag name, including a trailing `<`) and `escape_json_for_script` (script text only) now covers `+` chains, `%` and `str.format` (a prefix held in a name, returned by a helper of the file or passed as a literal argument counts), and a string built from such an output (`'' + safe_url(x)`, `'%s' % ...`, a helper that returns one, a `join` or container of it) is judged again where it is placed unless it opens its own markup; a bare output where nobody checked its position is not clean. Not covered, listed in the guard's docstring and #3864: an unreadable prefix is assumed position-neutral, a function that takes the output as a parameter and builds the tag, a lambda, a metaclass descriptor, hostile monkeypatching. A `+` chain longer than the depth bound is flagged instead of crashing the scan. Directed rows pin every rule.
