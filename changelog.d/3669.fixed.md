- **The native handlers of nine component tags dropped or invented `dj-*` event attributes the Python tag emits (#3669).** Under the socket render a click or input handler wired by the first, Django-engine render was missing or renamed. The nine tags, in six families: `dj_button`; `color_picker`; `pagination`; `data_table`; `nav_item`; `filter_bar` with `filter_select`, `filter_date_range` and `filter_search`. `dj_button` kept `dj-click` only while enabled, never emitted `dj-confirm`, and ignored `preset=` (a preset can carry `event` / `confirm`); `color_picker` ignored `swatches=`; `pagination` drew no numbered page buttons (each fires `next_event` with the page as `data-value`); `data_table` ignored `row_click_event` and the `prev_event` / `next_event` pager shown when `total_pages > 1` without `paginate`; `nav_item` with an `event` and a text body became a dropdown with no `dj-click`; `filter_bar` took each control's own `event` and never drew the "Clear filters" button. The Python tag is the reference. For `filter_bar`, a native block handler is handed only the rendered children, so each `filter_*` child now leaves its arguments in a comment that the bar reads, removes and draws with the Python tag's own renderer (`render_filter_bar`), which owns `event` and `clear_event`; a child outside a bar leaves an invisible comment where Django renders nothing; the default id stays `filter-bar` rather than a per-render random one. Whether a value wires an event is decided on the VALUE, not on its escaped text, so `confirm=None` / `False` / `0` / `[]` and `row_click_event=None` wire nothing, as in Python. `python/djust/tests/test_component_dj_attr_parity_3669.py` renders about 95 argument combinations of the twelve tags in the issue through both engines and compares the `(element, dj-attribute, value)` multiset, plus every falsy shape (`None`, `False`, `0`, `0.0`, `""`, `[]`, `{}`) for every event-bearing parameter, a hostile event-name sweep (quotes, `<`, `&`, `</script>`, U+2028) and a strict-CSP check on both engines. `combobox` and `toast_container` already agreed and are now pinned. Behaviour that stays different, and why: `tree_view` / `kanban_board` differ only for a `SafeString` operand (native escapes it, the safe side); the native `data_table` also wires about a dozen features the Python template never renders; the native bar and nav item see rendered children, so controls and sub-items inside `{% if %}` / `{% for %}`, a bar nested in a bar, and other content in a bar are drawn natively (as before) where the Python tag drops them; the string `"0"` and a lone space reach a handler as the number 0 and nothing (the engine hands handlers text); a block tag's unresolved-variable argument; a `nav_item` nested three levels deep; and the Python `data_table` template's own `sortable: False` quirk. Markup outside `dj-*` (classes, text, ids, ARIA) is #3663.
