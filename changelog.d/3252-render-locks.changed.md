- **Views of one connection have their own render locks and turn lanes; over SSE a slow handler in one view no longer delays the others, over WebSocket only `async def` handlers overlap (#3252).** The views of a connection (the page view and the `dj-lazy` / `mount_batch` views beside it) shared one render lock and one receive loop. Each view now has its own render lock, deferred-push queue and "event in progress" flag, and while a connection hosts several views its inbound frames (`event`, `url_change`, the view-addressed verbs such as `request_html` and `upload_register`, and the binary frames of an upload, which follow their register) run on a lane per view (`python/djust/_view_lanes.py`): one view's turns run in order, one at a time, beside other views' turns. Over SSE each POST takes its own view's lock and runs on its own thread, so views overlap whichever way their handlers are declared. **Over a WebSocket the limit is the connection's single synchronous thread:** handlers declared with plain `def`, and the connection-cleanup step every inbound frame makes before dispatch, run on it, so while a `def` handler blocks it no other view's frame is answered (two strict expected failures pin this); `async def` handlers, `start_async` work and awaits overlap. The isolation starts once a second view is mounted (a one-view page runs its frames inline, exactly as before; measured 1.6 ms per event before and after). Tearing a view down (`unmount`, mounting its container again, a navigation, the disconnect, the stream close) waits for the running turns of the views it releases; a view with 64 turns already waiting refuses further frames with `code: "view_busy"` (with `ref`, `target_id` and `event`; not retried). 23 regression cases in `python/djust/tests/test_multi_view_render_locks_3252.py` (two are strict expected failures).
