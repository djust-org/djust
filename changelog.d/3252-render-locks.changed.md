- **A slow handler in one view no longer delays the other views of its connection (#3252).** The views of a connection (the page view and the `dj-lazy` / `mount_batch` views beside it) shared one render lock and one receive loop, so a handler that took a second held up every other view's events, ticks, pushes and renders by that second. Each view now has its own render lock, its own deferred-push queue and its own "event in progress" flag, and while a connection hosts several views its inbound frames (`event`, `url_change` and the view-addressed verbs such as `request_html`) run on a lane per view (`python/djust/_view_lanes.py`): one view's turns run in order, one at a time, beside other views' turns. Over SSE each view's POSTs take that view's own lock (the page view's, or the slot's) instead of one session lock, and each turn keeps its own request. Tearing a view down (`unmount`, mounting its container again, a navigation, the disconnect or the stream close) waits for the turns of the views it releases, so nothing is released mid-handler; the receive loop itself no longer waits for an `unmount`. A view with 64 turns already waiting refuses further frames with `code: "view_busy"`. A page with one view runs its frames inline exactly as before (no lane, no extra task; measured 1.6 ms per event before and after). Known limit: over WebSocket, handlers declared with plain `def` still share the connection's single synchronous thread, so only `async def` handlers, `start_async` work and awaits overlap; see the multiple-views guide. Covered in `python/djust/tests/test_multi_view_render_locks_3252.py` (19 cases; the strict xfail that pinned the gap is removed).
