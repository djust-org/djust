- **Native Rust component and theme handlers read a bare positional operand's resolved text as `key=value` pairs, so attacker-controlled data passed as a positional argument could set any parameter of the tag; positional arguments were otherwise dropped** — `{% dj_tag name %}` with `name = "variant=primary"` rendered with `variant` set, and `{% dj_button label %}` with `"event=delete"` could set the click event name; `class`, `value` and the other parameters were reachable the same way. Output stayed escaped, so there is no markup or script injection. It affected the native `simple_tag`/`inclusion_tag` handlers in `djust_components` and `theme_tags` under the Rust engine. The same cause made `{% dj_tag "Python" %}` (valid Django, `label` is the first parameter) render an empty `<span class="tag tag-default"></span>`: the handlers skipped every argument without an `=`. The 67 such handlers that have a positional parameter now name each positional token after the parameter the Django tag's own signature declares at that position, at template compile time, through a new optional inline-handler hook `rewrite_args_at_parse(args)` (`djust._positional_args`), so `{% rating 4 %}`, `{% progress 25 %}` and `{% theme_mode_toggle "btn" False %}` render as their keyword forms and a positional value is only ever a value. Django's positional checks are mirrored with its messages (`received too many positional arguments`, `received some positional argument(s) after some keyword argument(s)`, `received multiple values for keyword argument`; Django reports a parameter given both by position and by keyword as a render-time `TypeError`, the Rust engine refuses it at compile time). **Not covered:** the raw `@register.tag` native handlers (`alert`, `card`, `accordion`, ...) are unchanged, and a bare variable whose value contains `key=value` can still set their parameters, in a template Django itself refuses (`Unexpected argument ... Use key=value format.`); that is tracked in a follow-up issue. (#3664)
