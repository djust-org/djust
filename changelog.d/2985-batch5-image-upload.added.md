- **ImageUploadPreview now ships its interaction on djust's upload pipeline (#2985, batch 5).** The component rendered a `dj-hook` that no shipped script answered and never sent a file anywhere. With the new `upload` kwarg (the `allow_upload()` slot name) its input carries `dj-upload` and its drop zone `dj-upload-drop`, so chunking, progress events, cancellation and every server-side check are `UploadMixin`'s; `components/static/djust_components/image-upload-preview.js` adds a thumbnail per chosen or dropped image from a browser object URL (revoked on remove, replace, when the server's own previews take over, and on teardown), a progress bar fed by `djust:upload:progress` with Cancel (`window.djust.uploads.cancelUpload`), Remove, UX-only pre-checks for type (`accept`), size (new `max_size`) and count (`max`, the server's previews included) that keep a refused file from being sent and say why, a refused-by-the-server state, drag and drop that becomes the same change event the picker produces, and polite announcements. The file input is now visually hidden rather than `display: none`, so the picker is reachable by keyboard. The `event` kwarg now means something: when the app names one it is sent once a selection has finished uploading, with `{count}` (untrusted). Markup changes are additive only (`data-upload`, `data-max-size`, `data-notify`, `dj-upload`, `dj-upload-drop` and two empty elements the hook fills), on the component class, template tag and Rust handler alike; a byte comparison of 7,683 renders against the previous release is identical once those are removed. The script registers in `window.DjustHooks` and only when neither hook registry already holds that name. 3 components from the issue remain.
