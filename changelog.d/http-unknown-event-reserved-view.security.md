- **The HTTP fallback refuses an event the page view has no handler for, and `view` is a reserved state field name.** Two low-severity findings from the 2026-10 explicit-path probes. (1) A POST naming an event that resolved to no attribute, or to a non-callable one, on the page view fell through dispatch and was answered with 200, a full render and a state save as if a handler had run; the socket transports and the component branch already answered 400. The page view now answers `{"error": "Event handler not found"}` with 400 and writes nothing. The event-name guard also used `$`, which matches before a trailing newline, so `"bump\n"` passed the syntactic check on every transport; it now uses `\Z`. (2) `ExposureContract` accepted `view` as a `state()` field name although the explicit render context reserves it for the view object; it is now rejected like the other reserved names. New cases in `test_http_unknown_event_refused.py`, `TestEventGuard` and `test_invalid_field_names_are_rejected`; seven existing tests that had pinned the 200 fall-through for an unknown event (three HTTP-fallback background-work tests, three sticky-child HTTP tests that now drive a handler the parent defines, and `TestErrorHandling.test_invalid_event_handler`) now expect the refusal.
