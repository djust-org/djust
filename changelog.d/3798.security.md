- **What a person typed into a password input can no longer be read back by a template under the native engine, on any form (#3798). Narrowly BREAKING for a template that branches on, or prints, such a value.** A bound `UserCreationForm` holds the typed password under `password1` / `password2`, which are no columns of `User`, so the model floor of #3790 (keyed on the model's field names) did not name them: `{{ form.password1.value }}`, `{{ form.data.password1 }}` and `{{ form.cleaned_data.password1 }}` printed the plaintext, as did every sibling spelling (`.data`, `.initial`, `form.data` / `form.initial` / `form.cleaned_data` as a whole or by iteration, a prefixed form's `u-password1`, `{% for f in form %}{{ f.value }}`, `visible_fields`, a `{% with %}` alias, a formset's `data` / `cleaned_data` / `initial`). A plain `Form` has no model floor at all (#3799), so the same read worked on any form with a password field.

  **The floor is now also keyed on the WIDGET.** A field whose widget is a password input (`PasswordInput` or a subclass, any widget with `input_type == "password"`, or a `MultiWidget` with such a part, whose per-part keys `pair_0` / `pair_1` are named too) is a floor field by type, whatever its name and whatever the form is (a `ModelForm` or a plain `Form`). It sits at the chokepoint #3796 built (`_model_form_floor` -> `_floor_field_readable`), so the form, bound-field and formset proxies and the engine's value conversion all hold it with no per-spelling code, and the Rust extension is unchanged. The test is one function, `djust.serialization.field_has_password_widget`, which `djust.forms.is_sensitive_form_field` (`persisted_form_input`) now asks too, so the two cannot disagree about what a password field is. A formset's own lists are read from the forms it built as well as the form class, so a field added in a form's `__init__` is held. djust's own `dj_form`, `combobox` and `rich_select` draw a password field blank whatever its widget class is called: a `PasswordInput` subclass under a name `_get_field_type` does not know fell to the text branch and printed `value="…"`.

  **What is NOT lost (measured).** Django's `PasswordInput` never writes a value back into the control (`render_value=False`), so `{{ form.password1 }}`, `{{ form }}`, `{{ form.as_p }}` and the errors of a typed-but-invalid form are byte-identical to Django's with and without this change, and a re-save posts what the person types now, not what was typed before. The view still reads `cleaned_data["password1"]` and `form.save()` still hashes it; the proxy replaces nothing on the form. **Migration:** a template that printed the typed value, or branched on it (`{% if form.password1.value %}`), now sees nothing and takes the else branch. Compute what the template needs in `get_context_data()`. The first refused read of each field is logged once, naming the field and never the value.

  **Not floored, by decision.** A plain `Form` field that is merely NAMED `password` over a text widget, and a plain `Form` handed `initial=model_to_dict(user)`, are #3799 (a name-based floor for every form would blank a login form's typed `password`; that is a product decision). `PasswordInput(render_value=True)` writes the value into the control on purpose and still does; the template's reads of it are refused. A view's own dict (`form_data`) is not a form. The Django template engine is unchanged.

  Regression cases in `python/tests/test_password_widget_floor_3798.py` and, as roots of the existing grammar, `python/tests/test_form_floor_differential_3790.py` (a bound `UserCreationForm`, a bound model formset over it, a bound and an unbound plain form with a `MultiWidget` and a late-added password field, and a plain-form formset, each x every producer x every sink, each with a Django-engine control that prints the secret). Each mechanism is gate-off tested separately.

  **Also stricter: `persisted_form_input`.** A field the new widget test classes as sensitive (a `TextInput` subclass with `input_type = "password"`, `TextInput(attrs={"type": "password"})`, a `MultiWidget` password part) is now refused by `persisted_form_input(...)` at view-class definition with `ExposureConfigurationError`. Before, such a typed value could be persisted to the server session. A view that declared one of these as persisted now fails at import: remove it from `persisted_form_input`, or give the field a real `PasswordInput`.
