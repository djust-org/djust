- **A relation read inside a filtered loop over a list of models renders empty on the Django-backend engine (#3888).** `{% for u in users|slice:':2' %}{% for g in u.groups.all %}{{ g.name }}{% endfor %}{% endfor %}` over a `list` / `tuple` of models (or a `QuerySet` at a nested name such as `page.users`) rendered nothing where Django's own engine prints the groups; so did `{{ u.groups.all.count }}`, `{{ u.groups.count }}`, a `*_id` attname such as `{{ p.content_type_id }}`, and the same reads behind `|first`, `|dictsort` and `{% with s=users|slice %}`. A model that reaches the engine inside a container used to be a dict of its fields, and anything the dict lacked was read through a loop alias that a filtered operand never registers. Such a model is now a **floored live handle**: the row carries its own handle through any filter, and the handle is the floor proxy the template sidecar already used, so every attribute read, relation traversals included, is checked against the serialization floor (the fields, methods, per-model rules and field types it withheld before stay withheld, the live handle refuses underscore-prefixed names for any reader, and anything a read returns is plain data or another floored handle (a model, manager or queryset becomes a proxy; a callable becomes a wrapper whose result is floored again; a class or module is refused, so `{{ u.DoesNotExist }}` renders empty; the wrappers report a class with no Python-level methods and close routes to Python-defined objects and namespaces: a UUID is its text, plain data is matched by exact type, a dict's keys are floored like its values, and a datetime or time with a Python-defined `tzinfo` carries a floor `tzinfo` that answers the same offset, DST and name questions), and `alters_data` methods are still never called). The rows a relation read returns (`u.groups.all`, `u.groups.first`) are handles too, so a second relation hop works. `{% if u == rows.0 %}` / `u in rows` compare models by class and primary key, `|dictsort:'field'` (dotted keys included) reads the key off the row once per row, `{{ u }}` is `str(u)`, and a model written as JSON for a tag argument or to a state snapshot is the same floored dict it always was. **Scope:** only a model that reaches the engine inside a container; a top-level single model on `DjustTemplateBackend` and on a LiveView is still serialised first and keeps the dict form (#3902), so `{{ u|pprint }}` of a top-level model dumps its fields while `{{ rows|first|pprint }}` prints its name. **Behaviour changes for a template that depended on the old dict:** a model in a container is no longer a mapping, so `{% for k, v in u.items %}` renders empty, as on Django; a bare `FileField` prints its stored name, as on Django (`{{ p.image.url }}` is the URL on both); a custom Python filter or simple tag that receives such a model gets the floor proxy (attribute reads work; `row["field"]` does not) where it got the dict, while a top-level model or a top-level queryset loop still gets the dict; and `{{ rows|json_script:"x" }}`, `{{ rows|pprint }}` and a data-dump tag such as `{% json_viewer %}` spell each model in a container as its `str()` (`["u0", "u1"]`) where they dumped its fields (Django raises for the `json_script` case), so code that reads such data in JavaScript must build the data explicitly. A bridged or native tag that takes a list of models as an argument (`{% data_table rows=rows %}`) still receives dict rows. LiveView state, the client payload and the msgpack snapshot are untouched. **Not in this change:** `dictsort` over a field the template reads nowhere else, on a QuerySet or in a LiveView, still renders empty (#3892).
