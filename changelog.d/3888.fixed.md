- **A relation read inside a filtered loop over a list of models renders empty on the Django-backend engine (#3888).** `{% for u in users|slice:':2' %}{% for g in u.groups.all %}{{ g.name }}{% endfor %}{% endfor %}` over a `list` / `tuple` of models (or a `QuerySet` at a nested name such as `page.users`) rendered nothing where Django's own engine prints the groups; so did `{{ u.groups.all.count }}`, `{{ u.groups.count }}`, a `*_id` attname such as `{{ p.content_type_id }}`, and the same reads behind `|first`, `|dictsort` and `{% with s=users|slice %}`. A raw model crossed into the engine as a dict of its fields, so anything the dict lacked was read through a loop alias that a filtered operand never registers. A raw model now crosses as a **floored live handle**: the row carries its own handle through any filter, and the handle is the same floor proxy the template sidecar already used, so every attribute read (relation traversals included) is checked against the serialization floor: `password`, `is_superuser`, `is_staff`, a `djust_exclude_fields` / `djust_serializable_fields` rule, a field-type exclusion, `get_session_auth_hash` and the other sensitive methods and every `_`-prefixed name stay unreadable, and `alters_data` methods (`delete`, `save`) are still never called. `{% if u == rows.0 %}` / `u in rows` compare models by class and primary key, `|dictsort:'field'` reads the key off the row (once per row) and fails closed to `""` for a floor field, and `{{ u }}` is still `str(u)`. **Behaviour changes for a template that depended on the old dict:** a model is no longer a mapping, so `{% for k, v in u.items %}` (which iterated the dict's keys `id`, `pk`, `__str__`, `__model__`, ...) renders empty, as on Django; a raw model's bare `FileField` prints its stored name, as on Django (`{{ p.image }}` was the URL; `{{ p.image.url }}` is the URL on both); a bridged tag handler (`{% regroup %}`, a custom tag) that receives a raw model receives the floor proxy instead of the filtered dict, so `row.username` works as it does on Django and `row["username"]` no longer does. LiveView state, the client payload and the msgpack snapshot are untouched (they hold the denylist dict, and a handle is never serialized; the LiveView path normalises a model in Python before it reaches Rust). **Also changed, and visible:** the rows a relation read returns (`u.groups.all`, `u.groups.first`) are handles too, so `{{ g.user_set.count }}` inside `{% for g in u.groups.all %}` under a `|slice` works (stage 2 of this issue, #3896), and `{{ rows|pprint }}` / `{{ rows|json_script:"x" }}` over a container of models spell each model as its `str()` (`[u0, u1]`, `["u0", "u1"]`) where they used to dump each model's field dict (`__model__`, `__str__`, every field), on both sides of the 100 000-row cap alike; a page that fed `json_script` a raw list of models must pass the rows it wants as data. **Not in this change:** `dictsort` over a field the template reads nowhere else, on a QuerySet or in a LiveView, still renders empty (#3892).
