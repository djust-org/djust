- **`{% include obj %}` and the component tags called a `render()` / `get_full_name()` marked `alters_data` or `do_not_call_in_templates` (#3815).** `render_template_object` (`python/djust/template/operands.py`) called `obj.render()` on a context object named by `{% include obj %}` with no look at either marker, on `DjustTemplateBackend`, a LiveView (HTTP GET and WebSocket), `RustLiveView` and `_rust.render_template`; the component tags `avatar_group`, `AvatarGroup`, `LiveIndicator` and `PresenceAvatars` called `user.get_full_name()` the same way. Stock Django does call such a `render`, so this was Django parity; **djust is now stricter than Django here on purpose**, on the rule the serializers already apply through `djust_core::template_call_guard` (#3772, #3778). A flagged `render` is not called and the include renders the empty string with a WARNING (it does not raise); a flagged `get_full_name` is not called and the avatar falls back to `str(user)`, the branch a blank name already takes. A marker read that raises anything but `AttributeError` refuses too (fail closed). An unmarked `render()` / `get_full_name()` is called exactly as before. `{% extends obj %}` was never affected (it reads a compiled template's source and does not call `render`). Regression cases in `python/tests/test_render_call_guard_3815.py` count the calls on a real payload, through every entry above plus Django's own engine as the control.
