- **`params_form_fallback = "fields"` keeps the fields that validated when `params_form` rejects the URL (#3874).** The default `handle_invalid_params()` hands `handle_params()` the initial value of every field, so `?page=abc&sort=name` lost the valid `sort=name` with the invalid `page`. A view that sets `params_form_fallback = "fields"` keeps every field that validated (it is not in `form.errors` and is in `form.cleaned_data`, filled from `initial` where the URL left it out, exactly as on a valid URL) and replaces only the failed ones with their initial value; a value that failed validation never reaches `handle_params()`. A form-level error (`clean()` raising without naming a field) and a URL past the form-data bounds keep nothing, because the fields that passed one by one are the combination the form refused (a `clean()` that names the field with `add_error()` is a field error and keeps the siblings, **provided the merged result still passes `clean()`**: it is run once more on a copy of the form with the kept values next to the replaced fields' initial values, and the view gets the plain initial values if `clean()` rejects it, so the result is always a combination the form accepts or the plain initials). `params_errors` is unchanged. **The default does not change:** `"initial"` stays what a view gets unless it opts in. A value other than `"initial"` or `"fields"` raises `ImproperlyConfigured` on every request of a view that declares `params_form`, and `manage.py check` reports it as V023, so a typo such as `"field"` cannot silently mean the default. Guide: Navigation, "Keeping what validated".
