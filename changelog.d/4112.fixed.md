- **Rows a view holds now show a handler's database write on every transport (#4112).** Over WebSocket and SSE a QuerySet kept on the view (`self._rows = Model.objects.filter(...)` in `mount()`, the documented pattern), a related-manager QuerySet held from `mount()`, or a `cached_property` listing rows kept answering with the rows from before the write; 1.3 behaved the same. Now a statement that changes rows, run in any step of the view (an event handler, `async def` or not, `mount()`, `handle_params()`, `start_async` / `@background` work, `handle_tick()`, a server push, `handle_info()`, the connection hooks, a component's handler; on any database alias), marks the view with the table it wrote. Before the view's next render, every held QuerySet that reads that table (its joins, subqueries, `union()` parts and `prefetch_related()` lookups with their through tables) is read again, once, and the view's cached properties are recomputed if its own queries read that table. A write to a table the view neither holds nor reads changes nothing: no re-read, and a handler that changed nothing on the view still answers `noop`. When a write's or a read's table cannot be determined, everything is read again (logged at DEBUG by `djust._held_rows`). A model instance (its prefetched relations included) and a list of rows stay snapshots on every transport. `self.rows_changed(*models_or_tables)` marks the view by hand for a write djust cannot see (a `SELECT` with side effects, `cursor.callproc()`, a thread or task the handler started, an `on_commit` callback, another process). A write that lands after the turn answered, from such a thread or an `asyncio` task the handler created, shows on the view's next render: nothing is sent by itself. Likewise a sticky or embedded view whose neighbour wrote re-reads on its own next render. The mark is kept until a render of the view succeeds.
