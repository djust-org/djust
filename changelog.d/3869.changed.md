- **`{% data_table %}` is one implementation on both engines (#3869).** Under Django's template engine the tag now renders the native table the Rust engine always drew: `data_table` is a simple tag that hands the same operands to `DataTableHandler` (`render_data_table`, rows and columns converted as the Rust engine hands them, so a model row is its serialised dict and the exposure floor holds). Every feature the tag documented but `table.html` never drew now works under DjangoTemplates (`expandable` draws `dj-click="on_table_expand"`, `editable_columns`, `exportable`, `reorderable`, `column_visibility`, `density_toggle`, `group_by`, `copyable`, `importable`, `row_drag`, `editable_rows`, `resizable`, frozen columns, virtual scroll, footer aggregations, conditional formatting ...). **The markup changes**: it is the native table's (no whitespace between elements, `data-row-key` on rows, the handler's classes and wrappers; the parity harness measured class, attribute and text differences in all 176 variants), so CSS or tests written against the old `table.html` markup may need new selectors. The parity row for `data_table` is `IDENTICAL` (it differed in all 176 variants). A `lazy` string or a `str` with `__html__` as a cell is text on both engines now (only `mark_safe` keeps markup in a cell); a generator or set of rows or columns is still read. The native header gained what the Django template had: a sortable `<th>` is keyboard-focusable (`tabindex="0"`), the sort-direction glyph is a decorative `<span class="data-table-sort-glyph" aria-hidden="true">`, and the loading skeleton has `aria-live="polite"` (the Rust engine's table lacked all three). Tests in `python/djust/tests/test_data_table_single_impl_3869.py`.
