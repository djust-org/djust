- **`{% include obj %}` in a child view's template called a `render()` marked `alters_data` or `do_not_call_in_templates` (#3880).** #3879 refused it on five entries (`DjustTemplateBackend`, `_rust.render_template`, `RustLiveView`, a LiveView's WebSocket and HTTP GET renders), but embedded and sticky child views (`websocket.py::render_embedded_child_html`, `templatetags/live_tags.py::_render_sticky_child_html`) render through Django's stock engine, which called it. The engine is unchanged (no change to filters, tags or escaping): the render is now made inside `include_guard_scope` (`python/djust/_include_guard.py`) and a patched `IncludeNode.render`, inert outside that scope, applies the same `refused_marker` check as the five entries, so a flagged `render` is not called, the include renders the empty string and one WARNING is logged per type. The operand is resolved once and the checked bound method is the one that runs. The same scope now wraps the other places a view's or component's context reaches Django's engine: the two remaining `{% live_render %}` branches (legacy non-sticky and lazy), streamed fragments, pending layouts, the native renderer, `dj_suspense` fallbacks, a component's Django-engine fallback and `{% extends %}` path (both component kinds), the template of an inclusion tag bridged into a LiveView render, and `LiveViewTestClient.render(engine="django")`. A render no djust view or component is making (your own page, the admin) is still stock Django. Regression cases in `python/tests/test_render_call_guard_3815.py` (the two child-view tests that pinned the old behaviour are flipped).
