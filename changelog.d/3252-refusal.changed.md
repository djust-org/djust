- **A refused lazy or batched view fails alone (#3252).** A view mounted beside the page view that the user may not see (login required, a missing permission or object permission, an `on_mount` redirect) answered with the page-level `navigate` frame, so one refused `dj-lazy` view sent the whole page to the login page. It now answers with a `view_refused` frame addressed to its container (over `mount_batch`, an entry of the reply's `refused[]` array, and no `navigate[]` entry): the client replaces that container's content with a short `role="alert"` message and, for a login or redirect, a link to the sign-in URL, sets `data-djust-refused="<reason>"` on it, forgets the view and fires `djust:view-refused` so an application can show its own prompt. The page's URL, the page view and the other views are untouched, on WebSocket and SSE; the refused view is torn down on its own, and a refusal at event time ends it the same way: a re-check that fails (`reauth_on_event`) refuses that view in its container (it used to send the whole page to the login page and close the socket; the page view's own failure still does), and an event for a refused or unmounted address over WebSocket now answers `code: "view_unavailable"` like SSE. The page view's own refusal is unchanged. **Upgrade note:** a client older than this release does not know `view_refused` and leaves a refused lazy view's container empty instead of navigating. `docs/website/guides/multiple-views.md` documents the frame, and states what stays as it is: lazy views reload fresh on Back and Forward, lazy views without any live transport are refused with `view_unavailable`, and a page of lazy views only needs a minimal page view over SSE. Covered in `python/djust/tests/test_multi_view_refusal_3252.py`, `tests/js/view_slots_3252.test.js`, `tests/js/sse_view_slots_3252.test.js` and `tests/playwright/test_multi_view_refusal.py`.
