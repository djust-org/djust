- **A form's stored data is now bounded by how many members it holds, not only how many characters (#3844).** `max_form_data_size` bounds characters, and characters do not bound time: every event hands ALL of the stored form data to the template engine (a Python pass per member, then the extension's `update_state`, about 0.7 microseconds a member), so 174 `validate_field` events of `[""] * 15000` stored 2.61 million empty members under the 2.6 million limit and made each later event take 0.03 s growing to 1.25 s (`[[]] * 7500`: up to 3.9 s) over a connection's own state. `LIVEVIEW_CONFIG["max_form_members"]` (default 100,000; `0` removes it, a value that is not a non-negative integer is the default, never unlimited) now counts every key, every value and every list, tuple, set or mapping inside them as one, however long a string is, and is judged by the same walk, early stops, nesting bound and replaced-entry arithmetic as the size limit, on every path that keeps a form's data (`FormMixin`, `WizardMixin`, the admin form view, a `params_form`); an event past it is refused whole and reported like the others, in `form_errors` / `wizard_step_errors["__all__"]` / `params_errors["__all__"]`, without the keys. **Behaviour change:** form data of more than 100,000 members over the socket is refused (a form with a multi-select of tens of thousands of options needs `max_form_members` raised, or `0`); the state sync itself still walks everything that is stored, so the cost of an event at the cap is bounded rather than gone: about 70 ms for flat strings or numbers, and roughly 0.2 to 0.4 s for container-heavy data (a list or mapping weighs one member, the same as a leaf; measured on a loaded machine). Each field counts as two members (its key and its value), so raising `max_form_fields` above about 50,000 needs `max_form_members` raised too. A wizard's member and character limits are the TOTAL across its steps, not each step's (#3858). Also: the exact-limit case inside a bulk container with pending non-leaf members is now pinned for both limits (the `>` to `>=` mutation in `_charge_rest` survived #3842's tests), and the lazy-provenance benchmark targets are 10x their measured medians, not 5x.
