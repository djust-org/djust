- **A page that emits a `<div dj-view="…" dj-lazy>` container now registers it, with the checks `{% live_render %}` applies when it registers a child (#3252).** Registration only, and deliberately additive: nothing renders, the response is byte-identical, and no state policy moves. The renderer records the containers it actually *emitted* — a container inside a branch that did not run is not among them — and each one is then resolved and authorized against the request exactly as a tag's child is: the `DJUST_LIVE_RENDER_ALLOWED_MODULES` prefix allow-list, resolvability, a `LiveView` subclass, `check_view_auth` and `enforce_object_permission`. A container that fails any of those is not registered, so no later event can name it, and there is no route from a client-supplied id to a class — only a lookup in the registry this builds. Provenance is structural rather than a marker in the output: the record is written from `Node::Text`, developer-authored template text, which attacker-controlled data cannot enter, so it arrives as a `Node::Variable` instead — the same argument the `dj-model` allow-list already rests on. A value whose text spells a container — a comment, a field, a `|safe` payload — therefore registers nothing, which is pinned by a test written to fail-to-forge. The `dj-lazy` attribute form is still not *delivered* over the page-POST fallback; this lands the registration half only. Two containers that author the same view are two containers, each with its own id (`_2`, `_3` suffixes, in document order) rather than one silently overwriting the other. 9 regression cases in `python/tests/test_lazy_container_registration_3252.py`.
