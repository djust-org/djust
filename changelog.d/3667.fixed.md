- **Native component handlers refuse the input the Python tags refuse (#3667).** Where the Python tag raised, the native handler rendered. Now a required parameter that nothing supplies is a `TemplateSyntaxError` at compile time with Django's message (`'data_table' did not receive value(s) for the argument(s): 'rows', 'columns'`, `djust._positional_args.missing_arguments`, a transcription of the end of `parse_bits`); `slider` raises `ValueError` for a non-numeric `value` or `value_end` instead of echoing it into the markup; `activity_feed` (`max`), `progress` (`value`) and `pagination` (`total_pages`) raise instead of falling back to a default, and `animated_number` raises for a non-string `separator`. `notification_center` with `notifications=None`, the one row that ran the other way, renders an empty list as the Python tag does instead of raising. `notification_popover` with a list of strings emitted `<built-in method title of str object at 0x...>` into the page in BOTH engines (a `str` has a `title`, the method, read with `getattr(item, "title", "")`); an item attribute that is callable now reads as absent. **Behaviour change:** a template that relied on the lenient rendering of one of these calls, and was already invalid under Django, now raises under the Rust engine. Unchanged and documented: an unknown keyword is still accepted by the native handlers that remain (`rust_only_keys` in the parity baseline; `dj_select` reads `options_var` on purpose). It is NOT accepted by six of the nine tags bridged under #3666 (`combobox`, `field_error`, `form_errors`, `relative_time`, `rich_select`, `toast_container`): they take the Python tag's keywords, so `{% toast_container toasts=t class="x" %}` now raises Django's `unexpected keyword argument` where it used to render. New `python/tests/test_native_handler_fidelity_3666_3667.py` derives the variants one engine alone rejects, over every tag, from `scripts/template-library-parity.py --fidelity`.
