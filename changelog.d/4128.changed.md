- **Saved view state can be switched off, and a subclassed session store now holds it.** `DJUST_AUTOMATIC_STATE = False` in settings saves nothing of any view between requests, and the class attribute `automatic_state = False` does the same for one view (`True` there overrides a project that switched it off). Explicit exposure is unchanged; only saving is. With it off nothing of the view's undeclared state, `_private` state, component state or changed/deleted record is written to the session on any transport, each page-POST fallback request runs `mount()` again and a socket reconnect starts from `mount()`. A field declared `state(..., persist="server")` is still kept: it was asked for by name. Only `True` and `False` are accepted; any other value is read as off and reported by the new system check `djust.C035`. This replaces 1.x's `view_state_in_session = False`, and the startup error for that removed key now names the replacement. **Check your session engine:** saved state and `persist="server"` fields now work with a `SESSION_ENGINE` whose `SessionStore` subclasses Django's `db`, `cached_db`, `cache` or `file` store, where earlier 2.0 pre-releases accepted only those exact classes. A project with such a subclass had nothing saved until now and will start saving view state in its session on upgrade; set `DJUST_AUTOMATIC_STATE = False` to keep saving nothing. An engine built on none of those stores (for example `signed_cookies`) still saves nothing, and the new system check `djust.C034` says so at startup and names both ways out. (#4128)
