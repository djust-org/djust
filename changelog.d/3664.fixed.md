- **Native Rust component and theme handlers take the same positional parameters as the Python tags** — `{% dj_tag "Python" %}` is valid Django (`dj_tag` is a `simple_tag` whose first parameter is `label`), but the Rust handlers read `key=value` strings and skipped every argument without an `=`, so the Rust engine rendered an empty `<span class="tag tag-default"></span>`. The 67 native `simple_tag`/`inclusion_tag` handlers that have a positional parameter, across `djust_components` and `theme_tags`, now render the positional form as the keyword form (`{% rating 4 %}`, `{% progress 25 %}`, `{% theme_mode_toggle "btn" False %}`). One mechanism, no per-tag list: the template engine gains an optional inline-handler hook, `rewrite_args_at_parse(args)`, called once at compilation with the tokens as written, and `djust._positional_args` renames each positional token after the parameter the Django tag's own signature declares at that position. This also closes a hole the old behaviour had: a positional value containing `=` (a context value `"variant=primary"`) reached the handler as resolved text and was read as a keyword, so a context value could set any parameter of the tag it was passed to. Django's positional checks are mirrored with its messages: `received too many positional arguments`, `received some positional argument(s) after some keyword argument(s)`, and `received multiple values for keyword argument` (which Django reports as a render-time `TypeError` when a parameter is given both by position and by keyword; the Rust engine refuses it at compile time). Raw `@register.tag` tags have no positional parameters (Django refuses a bare token) and are unchanged. The parity baseline moves 54 rows toward Django, none worse (#3664).
