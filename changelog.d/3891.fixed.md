- **`params_form_fallback = "fields"` hands `handle_params()` the value the valid path would for a kept field the URL left out or empty, when that field has an `initial` (#3891).** On a valid URL the form's `clean()` runs first and such a field then takes its `initial`, so `clean()`'s write to it is overwritten. The `"fields"` fallback filled the `initial` *before* its extra `clean()` check and then adopted `clean()`'s output, so `clean()`'s write survived: a `clean()` that copies a request value into another field handed a value that had failed validation to `handle_params()` through a field the URL never named. The `initial` fill is now applied again to the check's output, with the helper the valid path uses. The check itself still runs on the combination that would be handed over, so the result stays a combination `clean()` accepts, or the plain initials. Behaviour changes: a `clean()` that sets a default into such a field now loses to the field's `initial` (as on a valid URL), and the fallback hands over a copy of a mutable `initial` it fills in (the valid path and `"initial"` mode hand over the object itself, so a `handle_params()` that mutates it there changes the form class's default for later requests: [#3926](https://github.com/djust-org/djust/issues/3926)). Not covered, because the valid path shares it: a field with no `initial`, a `clean()` that also writes the field into `self.data`, and a multi-select field the URL left out ([#3922](https://github.com/djust-org/djust/issues/3922)). A field the URL supplied still keeps `clean()`'s output on both paths, a failed field is still its `initial`, and `"initial"` mode is unchanged. Guide: Navigation, "Keeping what validated".
