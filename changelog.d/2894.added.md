- **Block-tag forms for the container theme components (#2894, #3279).** `{% theme_card_block %}…{% end_theme_card_block %}` and `{% theme_alert_block %}…{% end_theme_alert_block %}` take a body of template tags, so a card can hold a button, a loop or an `{% if %}` without pre-rendering HTML in Python and passing it through a `|safe` slot. The convention is the inline tag's name plus `_block`, closing with `{% end_<name>_block %}`, and it covers every container whose body was a string: `theme_modal_block`, `theme_dropdown_block` (the menu), `theme_tooltip_block` (the wrapped content) and `theme_nav_group_block` (the items) as well. The inline tags are unchanged. A block form takes its inline tag's arguments except the one the block fills, and passing that argument (or its `slot_*` spelling) too is a `TemplateSyntaxError`. The body is rendered by Django's engine in the caller's context, so autoescaping applies to `{{ variable }}` inside it. Each block form calls its inline function, so the markup and the per-theme `card.html` overrides are the inline form's. They work in LiveView (Rust-rendered) templates through the `{% load %}` bridge. `djust_theme init --with-examples` now writes the block form. `{% theme_card %}…{% end_theme_card %}`, the spelling #2894 once documented, is still not valid. Regression cases in `python/djust/tests/test_theming_block_tags_2894.py`.
