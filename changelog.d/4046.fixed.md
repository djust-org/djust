- **Interactive components work over the HTTP fallback under explicit exposure** (#4046). A `DropdownMenu` and a keyed collection of them answered every page-POST event with 400 "Component not found": each request built a new view whose menus had new random ids and an empty registry. A declared interactive component is now part of the view's exposure contract: its id is derived from its declaration (view class, attribute name and, for a row, its key and that key's generation), and the id the page carries has a tag, an HMAC under `SECRET_KEY` (and `SECRET_KEY_FALLBACKS`) bound to the session, user, tenant, route and tab; an id from another session, user, tenant, route or tab, a bare derived id and a malformed tag are refused alike. Its state (open, selected, the observation cursor; each row's generation) is a small record saved in the view's declared `persist="server"` envelope, with its binding, expiry and size limit; `persist=False` on the declaration opts out. One restore (`djust._component_state.restore_component_state`, through `apply_declared_state`) and one lookup (`resolve_component_target`) serve the HTTP fallback, the WebSocket and SSE, so a reconnect also finds a menu as the last event left it, and an unmaterialized ADR-031 descriptor now falls through to the view's alias on the fallback as it does on the socket. Tabs: a row's generation changes only when `sync()` removes that key, and a save keeps the stored copy of the rows its view does not hold, so two tabs showing different rows of one route, a reload and Back/Forward leave each other's menus working. A genuine id whose row is gone gets the current page on the fallback (no action runs); a row that leaves the data without a `sync()` removal and comes back answers to its old id. A missing, expired or invalid record starts the menus from `mount()` and the event still routes; component records that do not fit the size limit are left out of the save (logged once) instead of refusing every turn. The parameter-contract manifest keys a component by the id the page carries, so the client's strict binding applies to these components. The catalogue's dropdown example and its page are no longer pinned to the legacy policy, and the guide's examples run through a page GET plus fallback POSTs again. State is per session and route, not per tab. New cases in `python/djust/tests/test_interactive_http_fallback_4046.py` and `tests/js/interactive_wire_id_contract.test.js`.
