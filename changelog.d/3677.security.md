- **`djust_theming` now sanitises every URL with the same allowlist `djust_components` uses, instead of its own denylist (#3677).** The theming tags kept a denylist (`javascript:`, `vbscript:`, `data:`, and since #3665 `livescript:` and `mhtml:`), so every scheme it did not name passed through 19 sinks in both engines: `theme_button`, `theme_nav`, `theme_nav_group`, `theme_nav_item`, `theme_breadcrumb`, `theme_avatar` `src`, and the `action` and `*_url` of every `theme_*_page` that has them. `blob:`, `file:`, `jar:`, `view-source:`, `intent:`, `ms-word:`, `feed:`, `ws:`, `git:` and custom application schemes are not script schemes in a current browser, so none of this is a script-execution hole today; a denylist ages badly, though, since every new dangerous scheme is a hole until someone adds it. The theming helpers now call a new `djust.components.utils.url_allowed` (the decision `safe_url` already made, now callable without its escaping) and the theming denylist is deleted. `url_attr` and `safe_url` behave as before and the components allowlist is not widened. What happens to a URL whose scheme is not `http`, `https`, `ftp`, `ftps`, `mailto` or `tel` (a relative URL is fine) depends on the sink:
  - **Data-derived sinks** (`theme_nav`, `theme_nav_group`, `theme_nav_item`, `theme_sidebar_nav`, `theme_breadcrumb` items, `theme_pagination`'s `url_pattern`, `theme_avatar` `src` (an inline `data:image/...` stays), and every `theme_*_page` `action` and link): `#`, as before. For example `sms:`, `geo:`, `webcal:` and app deep links such as `myapp://record/42` now render `#` in these tags; they passed through before. **This is the behaviour change for theme authors.**
  - **Developer-supplied literals** (`{% theme_button href=... %}`, and `href`, `src`, `action` or `formaction` passed through `**attrs`, for example to `theme_input`): a script scheme (`javascript:`, `vbscript:`, `data:`, `livescript:`, `mhtml:`, in any spelling a browser reads as that scheme) still raises `ValueError`, exactly as before. Any OTHER rejected scheme renders `#` and logs a warning naming the parameter, not the URL; it does not raise, because these sinks rendered such a URL before and `href=record.url` is data, so a `webcal:` or `blob:` value must not turn the page into a 500.
  - **`mark_safe` URLs** get no exemption in any theming sink: a marked-safe URL is made plain text before the template prints it, so it is judged and escaped like any other string, as `safe_url` does (an already-escaped `&amp;` therefore prints as `&amp;amp;`). Before, a template printed it raw, and `mark_safe("&#x6A;avascript:x")`, which the allowlist cannot see as a scheme, reached the page as a `javascript:` URL to a browser.

  The URL-scheme sweep (`scripts/template-library-url-sweep.py`) now reads every scheme outside the allowlist, not only the script schemes, with 20 new payloads in the forms a browser still reads as that scheme; run over the tags with the test corpus on `main` it reported 38 holes in the theming tags (19 sinks in each of the two engines), and the sweep test finds none after the change. `python/tests/test_theming_url_allowlist_3677.py` drives every theming sink in both engines and pins the set of sinks from the templates (every URL-bearing attribute, composite values included) and from the tag functions, so a new sink is a visible decision. That wider scanner also found one gap in `djust_components`, recorded and pinned, not changed here: the Rust `Avatar` (`crates/djust_components/src/simple/avatar.rs`) does not strip a leading C0 control character before reading the scheme, so `\x01blob:...` reaches an `<img src>` where the Python `url_attr` returns `#`. New cases in `test_theming_url_allowlist_3677.py` (replaces `test_theming_url_denylist_3665.py`), `test_theming_url_scheme_guard.py` and `test_url_scheme_sweep_3665.py`.
