- **A Django `Form` / `BoundField` bound by `{% for %}` or `{% with %}` renders under the Rust engine as it does under Django (#3755).** `{% for f in form %}{% field_error field=f %}{% endfor %}`, `{% with f=form.name %}{% field_error field=f %}{% endwith %}` and `{% for f in form %}{{ f.errors }}{% endfor %}` rendered nothing under the Rust engine and the errors under Django. The plain-backend render path flattened a form to `{name: SafeString(widget HTML)}` before the engine saw it, which keeps `{{ form.name }}` working and loses what a form *is*: iterating it yielded the field *names* (`{{ f.label }}` was empty), `f.errors` / `f.field.required` read attributes a string does not have, `form|length` was the number of fields (Django: 0) and `{{ form }}` printed a dict. With `for_render=True` the form now crosses as itself (`template.serialization.serialize_value`); the JSON-state paths (`normalize_django_value`, the LiveView bridge) still flatten. Two engine rules came with it, both measured against Django: a bridged Python tag now receives a live `BoundField` although a `BoundField` is iterable (`context::live_handle_is_form_object`, decided by `djust.serialization._is_form_object`; it adds no exposure, since the form the field came from already reaches the same tag live under its own name), and a `list` / `dict` *subclass that spells itself* crosses as the carrier whose `{{ v }}` is `str(o)` (`list_subclass_spells_itself`, the list half of #2899), so `{{ form.name.errors }}` / `{{ f.errors }}` is Django's `<ul class="errorlist">…</ul>` and not `['This field is required.']`, for a top-level `ErrorList` / `ErrorDict` / `OrderedDict` as well (`serialize_value` no longer rebuilds one as a plain container). **Behaviour change:** `{{ od }}` for a top-level `OrderedDict` and `{{ errors }}` for a top-level `ErrorList` / `ErrorDict` now print what Django prints (`OrderedDict({...})`, the errorlist markup) instead of a dict / list display. **Not covered:** a form held as LiveView *state* still reaches the template as `{name: widget HTML}`, because LiveView state is JSON (the LiveView bridge keeps the flattening, and does not put the form in the sidecar; tracked at #3767).
