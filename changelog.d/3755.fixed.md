- **A Django `Form` / `BoundField` bound by `{% for %}` or `{% with %}` renders under the Rust engine as it does under Django (#3755).** `{% for f in form %}{% field_error field=f %}{% endfor %}`, `{% with f=form.name %}{% field_error field=f %}{% endwith %}` and `{% for f in form %}{{ f.errors }}{% endfor %}` rendered nothing under the Rust engine and the errors under Django. The plain-backend render path flattened a form to `{name: SafeString(widget HTML)}` before the engine saw it, which keeps `{{ form.name }}` working and loses what a form *is*: iterating it yielded the field *names* (`{{ f.label }}` was empty), `f.errors` / `f.field.required` read attributes a string does not have, `form|length` was the number of fields (Django: 0) and `{{ form }}` printed a dict. With `for_render=True` the form now crosses as itself (`template.serialization.serialize_value`); the JSON-state paths (`normalize_django_value`, the LiveView bridge) still flatten. Four engine rules came with it, each measured against Django: (1) a bridged Python tag receives a live `BoundField` although a `BoundField` is iterable (`context::live_handle_is_form_object`, decided by `djust.serialization._is_form_object`). This is a new spelling of a reach that already existed, not a new reach: a bridged tag already got the live form under its own name, and the bridge has no serialization floor, so `{% some_bridged_tag x=f.form.instance.password %}` now prints what `x=form.instance.password` already printed (#3771; the PR's first version of this line said "adds no exposure", which was wrong for `json_viewer`, since fixed by keeping it on the floored native path, #3756). (2) A `list` subclass that overrides `__str__` / `__repr__` (Django's `ErrorList`) crosses as the carrier whose `{{ v }}` is `str(o)` (`list_subclass_spells_itself`, the list half of #2899), so `{{ f.errors }}` is `<ul class="errorlist">…</ul>` and not `['This field is required.']`; for `|json_script` the carrier is the array, as the dict-subclass one is the object (`Encoded::live_sequence_value`), so `{{ form.errors|json_script:'e' }}` is the errors as JSON. (3) A top-level `ErrorList` / `ErrorDict` in the context is no longer rebuilt as a plain container by `serialize_value` (limited to subclasses that define `__html__`; a top-level `OrderedDict` is rebuilt as before). (4) An object whose `str()` / `iter()` raised at conversion stays iterable by TYPE, so `{% for f in form %}` over a form with one broken widget renders the loop and the real exception appears where the broken field is rendered, as in Django, instead of `'Form' object is not iterable`. A `Form` / `BoundField` is also carried like a one-shot iterator (handle live, items read at the sink), which removes the eager subwidget enumeration. **Behaviour change:** `{{ errors }}` for a top-level `ErrorList` / `ErrorDict`, and any `list` subclass with its own `__str__` / `__repr__` reached through an object, now print what Django prints (the errorlist markup) instead of a list / dict display. **Cost:** a form in the context of a template rendered through `DjustTemplateBackend` costs more per render than the flattened dict did (0.86 ms against 0.31 ms for four fields, 3.5 ms against 1.3 ms for twenty, release build), because the engine converts an object eagerly, `str(form)` included; the LiveView path is unaffected; tracked at #3769. **Not covered here:** a form held as LiveView *state* still reached the template as `{name: widget HTML}`, because LiveView state is JSON (fixed in #3767).
