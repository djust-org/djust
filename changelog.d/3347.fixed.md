- **The post-event session save merges what the view changed instead of overwriting the whole session (#3347).** A legacy `enable_state_snapshot` view loads its Django session once at mount and its per-event save wrote that whole copy back, so a value another tab, request, middleware or handler stored since (an idle-activity timestamp, a flag) was rolled back and a key deleted elsewhere came back; explicit `persist="server"` saves had the same window for the length of a turn. The save now records the keys written or removed through the session object it holds (djust's own `liveview_*` and `_djust_explicit_*` keys, and a handler's or `check_permissions`' own `request.session` writes, including an in-place change to a mutable value that was read), reads the session as storage holds it right before writing, applies only those changes to it and writes the result. It costs one extra session read per save; on `db` and `cached_db` sessions whose database can lock a row (not SQLite) the read takes the row lock in the same transaction as the write. A writer that saves its whole session from an older read, and sessions with no row lock (SQLite, `cache`, `file`), can still race it between the read and the write. A write made while a save is still running is kept for the next save, and a reference to a list or dict held in the session stays attached across saves. On `cached_db` the cache is written after the transaction ends. `signed_cookies` sessions cannot be merged and behave as before, as does the save after a handler's `logout()`, `flush()`, `clear()` or key rotation (merging resumes with the next event). Tested end to end over WebSocket and SSE on `db`, `cache` and `cached_db`, and on `file` at the save.
