- **An HTTP-only page on the default session policy leaves its loading state on the first POST** (#3635). A page that loads after its first render (`start_async` / `assign_async` queued in `mount()` or `handle_params()`) and is served to a client that never opens a socket or SSE stream stayed on its loading skeleton for good: the GET cannot run the queued work, saved the loading state in the session, and every page-POST fallback restored it without running `mount()`'s work. The GET now records a digest of the loading state it saved (`<view key>__mount_work`) when work is still owed. The first POST that finds the saved state unchanged runs `mount()` again, puts the saved state back on top and runs the work over it before the handler, after every refusal; the loaded state is then saved and the work is not repeated. State another writer saved in between invalidates the digest, so nothing is run twice. `mount()` therefore runs twice for such a page, as it does between a GET and a socket mount. A view whose `mount()` queued nothing records nothing.
