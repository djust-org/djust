- **The `Large LiveView state` warning now also fires when a view grows past the threshold after it was created (#3632, part 3).** `InMemoryStateBackend.set()` was the only caller of the warning, and the view calls it once at creation (empty state) and again when a stored snapshot is re-used, so a view that grew large during its life was not reported until the next reload. `refresh()`, the post-render store, now reports it too: once per cache key while it stays over the threshold (not once per event), again if it drops back under and grows past it again, and with the same breakdown. In-memory backend only (Redis has no large-state warning). The warning, from `set()` as well, now names the state by a short hash (`state-1a2b3c4d`) instead of the cache key, which holds the Django session key and the request path (the older ERROR lines of the in-memory and Redis backends, for a corrupt snapshot or a failed serialisation, name the same label; they used to print the raw key); `refresh(..., warn_on_large_state=False)` is honoured, and a warning that a `-W error` filter turns into an exception is logged, not raised, inside the render path. `refresh()` already serialises the view on every render, so the check reuses that snapshot (`len()` and a set lookup); the breakdown is decoded only on the render that crosses the line. Stream rows in the stored state and stream/temporary-assign rows in the stored tree (parts 1 and 2) are not changed: clearing stream items after each render removes every row from the page on the next event (measured; `test_stream_state_weight_3632.py`), so those remain open in #3632. New cases in `TestRefreshWarns`, `TestRefreshCost`, `TestTheRealConsumer` (`test_large_state_refresh_warning_3632.py`). Refs #3632.
