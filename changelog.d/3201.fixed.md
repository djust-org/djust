- **An explicit view mounts fresh over the WebSocket when its session no longer exists (#3201).** After a Redis flush or restart with cache sessions, eviction, expiry or `clearsessions`, the browser still presents the old session cookie. The mount's first storage read cleared that key, and binding the view's state to it then failed with "Protected view operation failed" on every reconnect, so the page was stuck until a manual reload. The mount now creates a replacement server session in that case, re-derives the user from it (anonymous, since a lost session cannot vouch for the user the socket connected as) and runs `mount()` with nothing restored. Only a key that was presented and then found missing is replaced: a socket with no session cookie is refused as before and creates nothing, a session that still exists keeps its identity, repeated mounts on one socket reuse one replacement, and the replacement expires after `DJUST_SERVER_STATE_MAX_AGE` because no cookie points at it. With `cache` sessions Django treats a failed cache read as a missing session, so a transient read error also mounts anonymous (the real session survives). A live socket whose session disappears is still refused with 4403, because that is how a logout revokes it; the reconnect that follows now mounts fresh. New cases in `python/djust/tests/test_exposure_stale_session_mount_3201.py`.
